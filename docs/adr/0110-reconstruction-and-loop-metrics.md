# 0110 重建评测与发现、分析、自愈 PR 三个环节的度量

## 背景

DESIGN §14.2 的 reconstructed 模式要在保留期内重新查询、按当前代码重新给出成绩。原有实现只把只读工具换成配置的 MCP 工具，研判输入（事件、阶段 A 的证据卡、子图）仍取自快照，事件收敛、证据链与领域包的改动在成绩上看不出来。第二阶段的验收（发现、分析、自愈 PR）还需要按故障计的事件数、根因命中、unlabelled 占比、检测延迟、证据卡覆盖、证据卡与告警的一致程度，以及 PR 的触发、可应用与正确，这些都不是按研判运行计的指标。

## 决定

1. **标注文件**：一个 YAML 文件列出全部故障标注（`apps/srenautix/src/eval/labels.ts`）。每条标注给出故障窗口与分析时刻、属于这次故障的告警（告警名与标签子集）、可接受的根因组件键、粒度、机制、处置判断、发现环节的成员要求（每项一组同义键）与变更时刻、快照模式对应的种子用例、防泄漏的 `learned_from` 取值、标准修复（仓库、提交、按文件与 JSON Pointer 给出的期望取值）以及依据。标注含部署方集群的事实，只保存在部署方本地。`eval label` 把标注写进对应的种子用例的新版本，快照模式使用同一套标准答案。
2. **重建包**：`eval export` 按标注从指标后端与 SreNautix 状态库只读导出（状态库会话设为只读，连接后核对）。告警来自 `ALERTS_FOR_STATE` 与 `ALERTS{alertstate="firing"}` 的 30 秒区间查询：同一组标签下 pending 开始时刻不同即为不同实例，只 pending、从未 firing 的不算；实例从第一次观察到 firing 起接入，结束时刻的精度是一个步长。拓扑来自 kube-state-metrics 历史（ADR 0033）与状态库的 `topology_events`，同一个键两者都有时以状态库为准；变更来自状态库的 `change_events`。范围是故障窗口往前一个归并相邻时间，拓扑与变更再往前 24 小时。包保存在用例目录的 `bundles/` 下。
3. **重放**：`eval reconstruct` 用 server 的同一套代码按 30 秒一步重放：告警经 `resolveAlert` 接入（节点查找与状态库的 `find` 规则相同，包括墓碑与不带 API 组的 kind），每一步取触发中与相邻时间内结束的告警、窗口内的变更源变更与从拓扑事件推导的发布（ADR 0104），`computeIncidents` 后与上一步的事件 `reconcileIncidents`，记录每个事件第一次出现的时刻、曾经的成员与各版本引用过的变更。
4. **发现指标**（每次故障）：曾经包含故障告警的事件数；主事件（包含故障告警最多）在窗口结束时的根因是否在标注的根因集合内；主事件是否覆盖要求的成员、某个版本是否引用过标注时刻前后 2 分钟内的变更；窗口内新建事件中没有根因的比例；检测延迟为首个故障告警的 pending 开始到故障告警第一次成为事件成员，重放开始前就在触发的告警不计（它们在重放起点接入，不代表检测）。事件数不超过 2、根因命中、成员与变更齐全为通过。
5. **分析**：在分析时刻取主事件，按阶段 A 的代码路径执行证据链（`PackEvidence.run`，评估时刻为分析时刻）、排除规则与报告，按 worker 的方式组装研判输入（两跳子图、动作目录、相关知识、查询模板）。快照的来源记为 `reconstructed`（契约 2.15.0）。阶段 B 的查询模板在同一时刻执行，与 server 的 `/v1/research/tasks/{run_id}/query` 相同。每个标注是一个用例（`label:<id>`），每条路由运行 k 次，评分、置信区间与报告沿用 ADR 0084；重建没有得到包含故障告警的事件时，这个用例的每次运行记为失败。另报证据卡覆盖（卡数、得出结论、异常、根因上的异常）。
6. **证据卡与告警结论一致率**：告警目录条目可以声明 `primary_card`（契约 2.15.0），即与告警条件对应、告警触发时应当判为异常的卡。对每条在分析时刻（重建）或报告渲染时（影子环境）仍在触发的成员告警，按告警实体取主卡的结果，以及条目全部证据链在该实体上的卡的综合结果（有一张异常即为异常）。一致率 = 异常 /（异常 + 正常 + 无法判定 + 没有卡）；没有目录条目、没有声明主卡、告警没有实体的单独计数。主卡判为正常或无法判定的告警按告警名与主卡列出。
7. **自愈 PR 指标**：研判输出的 `gitops_pr` 提议记入每次运行的记录。触发率 = 标注有仓库修复且结论为 likely 或 evidence_consistent 的运行中提议了 `gitops_pr` 的比例；标注没有仓库修复却提议的记为误触发。补丁在分析时刻 base 分支的提交上用临时索引文件执行 `git apply --check --cached`（不检出、不改动工作区），可应用后逐条核对标准修复的期望取值。
8. **影子环境统计**：`eval live` 只读查询状态库：时间窗口内新建且首次触发不早于窗口起点的事件数、unlabelled 占比、检测延迟（`first_firing_at` 到 `created_at`）的 p50 与 p95、阶段 A 有证据卡与有结论卡的比例、研判结论 likely 及以上的事件、证据卡与告警结论一致率、`gitops_pr` 提议、关联的 PR 与打开的 issue。
9. **数据缺失时的回退与标注修订**：
   - 状态库没有记录的 ReplicaSet 用 kube-state-metrics 历史推导发布：第一次出现即为新的 ReplicaSet，重建包起点就存在的不算，属主取 kube-state-metrics 的 owned_by，管理应用取状态库的 managed_by。reader 的 history/ksm 在线上遇到同样的缺失时也是这样补的。
   - 回退之后仍然无法重建的故障，在标注清单中单独列出，不从分母中去掉。
   - 标注可以分开写两个环节的标准答案：`discovery_roots` 是发现环节可接受的根因，`roots` 是分析环节的。例如迁移失败时，发布与迁移是变更源头，发现环节可以落在它们上；分析环节必须指出受影响的数据库。
   - 每次修改标准答案都在标注的 `revisions` 中写明日期、改动与理由。趋势表同时保留修订前后的分数。
10. **基础设施失败与研判记录**：
   - 模型路由不可达（连接失败、熔断）时评测立即停止，不写成绩单。
   - `--trace <目录>` 为每次运行写一份研判记录：标准答案、输出、检查与卡、账本、步骤、模型调用的完整请求与响应、工具调用。供诊断阶段 B 使用。
11. **故障域**：评测时路由的 `failure_domain` 不参与提前熔断（snapshot 与 reconstructed 两种模式都是）。故障域描述研判时刻路由对事件所在组件的依赖，例如路由经过被研判的集群本身；回放的是历史事件，路由此刻的健康与它无关。生产中这类事件只出阶段 A 的比例由影子环境统计反映，不进入分析成绩。
12. **预算**：评测只按单次运行的 `--max-tokens` 截停；每天的额度由运行评测的人在运行前扣除当天已用量后给出，成绩单写明本次用量。

## 结果

- 在 ADR 0104 的发布事故夹具上，重放把发布与回退的告警收敛为不超过 2 个事件，主事件根因是发布的目标，成员与 16:24 的回退齐全，检测延迟不超过一步（单元测试）。
- 导出、重放、阶段 A 与研判输入、查询模板、只读会话在真实的 VictoriaMetrics 与 PostgreSQL 上测试；补丁检查在真实的 git 仓库上测试正确、取值不对、不能应用与误触发四种情况。
- 重建包读取的是保留期内的数据：超出指标保留期的故障只能用快照模式评测；kube-state-metrics 历史没有 Argo 应用与版本标签，状态库还没有记录的时段推导不出发布。
- 主卡需要领域包逐条声明；没有声明的条目只有链级一致率。
