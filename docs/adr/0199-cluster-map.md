# 0199 全集群地图

状态：已采纳

## 背景

拓扑页原来只有覆盖表、邻域图和版本差异。邻域图要先输入一个组件键，只能看到这个组件两跳以内的对象，回答不了"集群里哪里坏了，会波及谁"。

2026-11-12 在参考部署（CCHP）上读到的拓扑有 1448 个对象、2351 条边：245 个 Pod、156 个 ReplicaSet、90 个 CRD、57 个 Argo CD Application、57 个 AppProject、172 个 RBAC 对象、95 个网络策略。把对象图原样画出来没有意义。

## 决定

拓扑页加"集群地图"视图，并作为默认视图。地图是按组件归并、按业务领域与服务分组的拓扑，正在触发的事件直接标在组件上。

### 1. 地图上画什么（`clusterMap`，`packages/core/src/topology/map.ts`）

| 对象 | 画法 |
|---|---|
| 有 Pod 的顶层对象（沿 `owned_by` 向上，Deployment、StatefulSet、CNPG Cluster、Workflow……） | 组件，Pod、ReplicaSet、属于它的 Service、PVC 计入成员 |
| 静态 Pod（属主是 Node） | Pod 自己是组件 |
| 有 `routes_to` 的对象（HTTPRoute、Ingress） | 组件（入口） |
| Service、带 Operator 约定的 Secret | 连接：经过它们的边接到它们选中或指向的组件 |
| 组件引用、挂载的其余对象（ConfigMap、Secret、PVC、PV……） | 不画，按类型计入组件的 `attachments` |
| Node | 不进图，画成地图下方的节点条；组件记下成员 Pod 运行的节点 |
| 集群枢纽（CoreDNS、CNI、CSI 驱动） | 不画边，列出直接依赖它的组件数 |
| 其余顶层对象（RBAC、CRD、策略、GitOps 对象） | 不画，只给出数量 `omitted` |

边是组件之间的依赖（from 依赖 to），同一对组件只有一条，记下关系列表、合并的对象级边数、最高的置信度与它的来源。`owned_by`、`scales`、`runs_on`、`managed_by` 不是依赖边。

组件的服务按 ADR 0193 的服务目录求：组件自己命中服务成员，其次它的某个成员（例如 Pod）命中，再其次命名空间的默认服务，都没有时不归属。

### 2. 接口

`GET /v1/topology/map?cluster_id&at`（契约 2.61.0）。结构部分只随拓扑版本与领域包变化，现在时刻的结构按集群缓存一份；事件每次重新读取：那一刻正在触发（或者 `at` 时刻在触发）、没有被抑制、调用方读取作用域内的事件。根因不是地图上的组件时沿 `owned_by` 求它的顶层对象；根因不在拓扑里（领域包的伪组件）时 `component` 为 null，按主服务计入服务框。

### 3. 排布

参考部署的地图用 elkjs 的嵌套分层布局（`hierarchyHandling: INCLUDE_CHILDREN`）试过：框散布在整张画布上，大部分边是全部组件到指标库与 OTel Collector 的引用，画面是一团线。改为确定的排布（`packMap`）：

- 服务框里组件按名称排成网格（不超过 12 个时最多 3 列，更多时 4 列）；服务框在领域框里上下叠放。
- 领域框按重要程度（核心、支撑、底座、运维自身，未归属最后）依次填进若干列，列数取外框最接近 16:10 的。
- 同一结构每次得到同样的位置，值班的人能记住"网关在左上角"。

同一服务里类型、命名空间、名称词干与连接都相同、不是事件根因的组件合并，阈值 3（`MAP_FOLD_MIN`，常见的三副本控制面与有状态服务）。名称词干去掉节点名、运行编号与哈希后缀：三个控制面节点上的 `kube-apiserver-<节点>` 合成 `kube-apiserver × 3`，每次一个的 `cchp-discover-<编号>` 合成一组。

### 4. 事件与边

- 根因组件按严重度着色（critical 红，其余橙），沿依赖边反向能到达根因的组件（依赖它的组件）标为受影响。传播只走置信度不低于 0.7 的边（`BLAST_MIN_CONFIDENCE`）：网络策略推断的边（0.6）只说明流量被允许；在参考部署上沿它传播会把同一命名空间里互相放行的 Dragonfly、NATS 都标成 PostgreSQL 的受影响组件。
- 领域框与服务框的边框取框内最重的状态，标题写未恢复的事件数。
- 依赖边默认只画事件的传播路径（两端都是根因或受影响的组件）；指向或选中组件时画出它的边；"全部依赖"开关画出全部。
- "只看异常"只留下根因、受影响的组件与有事件的服务。

### 5. 交互

画布交互从根因子图抽到 `GraphCanvas`（`packages/ui/src/domain/GraphCanvas.tsx`），根因子图、拓扑邻域与地图共用：缩放 0.1–4 倍、拓扑页上滚轮直接缩放、全屏、查找、指向突出、小地图、侧栏（ADR 0191、ADR 0197 的行为不变）。地图另外有：

- 缩小到 0.45 倍以下只显示组件名称；领域标题随缩放放大，看全图时也读得出。
- 单击组件打开侧栏：业务领域与服务、归属来源、成员、引用与挂载、所在节点、它依赖与依赖它的组件、未恢复的事件（链接到事件详情）、邻域与搜索链接。双击组件打开它的邻域，双击合并的组在图上展开。
- 节点条：指向组件时标出它所在的节点；指向节点时只突出运行在上面的组件。

控制台每 15 秒取一次地图；结构的指纹（拓扑版本、组件与归属、边数）不变时不重新排布，事件经 context 更新，节点对象不变（ADR 0191 §7）。收件箱的业务领域卡片后面加一张"集群地图"卡，选中了领域时地图对准这个领域（`/topology?cluster&domain`）。

## 考虑过的方案

- **把对象图原样画出来**：参考部署 1448 个对象，大多数是 RBAC、CRD 与 GitOps 对象，与"哪里坏了"无关。
- **elkjs 嵌套分层布局**：见 §3，参考部署上读不出来；分层布局留给邻域图，那里节点少、依赖方向是读图的依据。
- **默认画全部依赖边，靠变淡区分**：参考部署 137 条边中大部分指向指标库与 OTel Collector，变淡后仍然盖住组件。
- **按命名空间分组**：参考部署有 21 个命名空间，业务含义弱，与收件箱的业务领域分组不一致。接口里组件带命名空间，以后可以加切换，不需要改接口。
- **把节点画成普通组件**：每个组件多 1–3 条 `runs_on` 边，十个节点会把图拉成一团；节点条保留了"谁在哪台机器上"。

## 结果

在参考部署 2026-11-12 的拓扑（版本 816391）上：

| 项 | 值 |
|---|---|
| 对象 / 边 | 1448 / 2351 |
| 地图组件 / 依赖边 | 126 / 137 |
| 节点 / 枢纽 / 不画的对象 | 10 / 3 / 787 |
| `clusterMap` 耗时、返回体 | 25 毫秒、68 KiB |
| 浏览器首帧 | 150 毫秒 |

地图同时暴露了两处数据缺口，它们不在本 ADR 里修：

- 网关到 PostgreSQL、Dragonfly 没有依赖边：连接串在 Secret 里（reader 不读 Secret 的值），出口策略是 CiliumNetworkPolicy（reader 只解析 NetworkPolicy）。数据库出事件时网关不会被标为受影响。
- 领域包按告警的伪组件（`kind: component`）声明服务成员，真实对象（例如 `Deployment:cchp-prod/archive-exporter`、`Cluster:cchp-data/cchp-postgres`）落到命名空间默认服务或内置包的服务里；50 个组件没有归属。地图的虚线框与"未归属"领域就是给领域包补成员用的。
