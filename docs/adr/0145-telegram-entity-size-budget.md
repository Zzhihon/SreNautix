# 0145 Telegram 消息按实体总大小分配链接

## 背景

真实事件（Zzhihon/SreNautix#13 第 2 项）：CCHP 影子同步之后，Telegram 的 editMessageText 返回 400 `ENTITIES_TOO_LONG` 110 次，大事件的消息无法更新。

ADR 0125 只限制了两项：

- 解析后的文字不超过 4096 个 UTF-16 code unit；
- 实体数不超过 100。

这两项都没有超。超的是第三项：实体列表在 MTProto 里序列化之后的总大小。

- Bot API 文档没有写这一项。tdlib/telegram-bot-api#165 的维护者称"9500 字符是实体总大小当前上限的不错近似"。
- 第三方实测：20 个链接、URL 共 9600 字符可以发送，9640 字符被拒绝。按 TL 序列化分别是 9928 和 10008 字节，上限约 10000 字节。
- 每个实体是构造号、offset、length 各 4 字节，引用块多 4 字节 flags，text_link 再加 URL 的 TL 字符串（长度前缀 1 或 4 字节，加 UTF-8 内容，按 4 字节对齐）。实体列表本身另有 8 字节。

CCHP 的 vmalert 把 generatorURL 设成预填了规则表达式的 Grafana Explore 页面（`-external.alert.source`），表达式先做 JSON 转义再 URL 编码，每个链接 700 多字符。70 个成员告警、53 张卡的事件，组装出的链接序列化后超过 2 万字节。现有逻辑按个数分配实体，链接排在段标题之后，所以分到实体的 29 个链接一共 12,000 字节。

## 决定

`buildHtml` 在实体个数之外再按总字节数 `MAX_ENTITY_BYTES = 9000` 分配，比实测上限留 10% 余量。

- 段标题、引用块，以及最多可能分到的强调、等宽实体，先留出它们的字节。
- 链接按输出顺序逐个分配：放得下就带链接；放不下的只输出文字，后面较短的链接照样可以分到。
- 文字长度不受影响，删减规则与标签闭合不变。前面的段（告警来源、根因）优先分到链接，证据链里靠后的长链接最先退成文字。

测试：

- `test/support/telegram-html.ts` 按 Bot API 的规则严格解析（标签与属性白名单、成对闭合、blockquote 与 a 不能嵌套、code 里不能有其他实体、`&` 必须转义），并独立计算序列化大小；
- 所有 Telegram 黄金用例都要求不超过 `MAX_ENTITY_BYTES`；
- 新增 70 个成员、53 张卡的黄金用例 `large-incident.telegram.html`，链接形式与 CCHP 相同。

| 70 个成员、53 张卡 | 之前 | 之后 |
|---|---|---|
| 解析后的文字 | 4075 | 4075 |
| 实体数 | 100 | 100 |
| 链接实体 | 29 | 19 |
| 实体总大小 | 12,000 字节（被拒绝） | 8,656 字节 |

不采用的做法：

- **缩短链接**：需要在控制台加一个跳转服务，并保存链接；而且被拒绝的是整条消息，不是某个链接。
- **把链接放进按钮**：一条消息的按钮也有上限，按钮用于操作。
