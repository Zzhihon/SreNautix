# 0145 Telegram 消息按实体总大小分配链接

## 背景

真实事件（Zzhihon/SreNautix#13 第 2 项）：CCHP 影子同步之后，Telegram 的 editMessageText 返回 400 `ENTITIES_TOO_LONG` 110 次，大事件的消息无法更新。

ADR 0125 只限制了两项：

- 解析后的文字不超过 4096 个 UTF-16 code unit；
- 实体数不超过 100。

这两项都没有超。超的是第三项：实体列表在 MTProto 里序列化之后的总大小。

- Bot API 文档没有写这一项。tdlib/telegram-bot-api#165 的维护者称"9500 字符是实体总大小当前上限的不错近似"。
- 第三方实测：20 个链接、URL 共 9600 字符可以发送，9640 字符被拒绝。按 TL 序列化分别是 9928 和 10008 字节，上限约 10000 字节。
- 每个实体是构造号、offset、length 各 4 字节，引用块多 4 字节 flags，text_link 再加 URL 的 TL 字符串（长度前缀 1 或 4 字节，加 UTF-8 内容，按 4 字节对齐）。实体列表本身另有 8 字节。

CCHP 的 vmalert 把 generatorURL 设成预填了规则表达式的 Grafana Explore 页面（`-external.alert.source`），表达式先做 JSON 转义再 URL 编码，每个链接 700 多字符。70 个成员告警、53 张卡的事件，组装出的链接序列化后超过 2 万字节。现有逻辑按个数分配实体，链接排在段标题之后，所以分到实体的 29 个链接一共 12,000 字节。

## 决定

`buildHtml` 在实体个数之外再按总字节数 `MAX_ENTITY_BYTES = 9000` 分配，比实测上限留 10% 余量。

- 段标题、引用块，以及最多可能分到的强调、等宽实体，先留出它们的字节。
- 链接按输出顺序逐个分配：放得下就带链接；放不下的只输出文字，后面较短的链接照样可以分到。
- 文字长度不受影响，删减规则与标签闭合不变。前面的段（告警来源、根因）优先分到链接，证据链里靠后的长链接最先退成文字。

测试：

- `test/support/telegram-html.ts` 按 Bot API 的规则严格解析（标签与属性白名单、成对闭合、blockquote 与 a 不能嵌套、code 里不能有其他实体、`&` 必须转义），并独立计算序列化大小；
- 所有 Telegram 黄金用例都要求不超过 `MAX_ENTITY_BYTES`；
- 新增 70 个成员、53 张卡的黄金用例 `large-incident.telegram.html`，链接形式与 CCHP 相同。

| 70 个成员、53 张卡 | 之前 | 之后 |
|---|---|---|
| 解析后的文字 | 4075 | 4075 |
| 实体数 | 100 | 100 |
| 链接实体 | 29 | 19 |
| 实体总大小 | 12,000 字节（被拒绝） | 8,656 字节 |

不采用的做法：

- **缩短链接**：需要在控制台加一个跳转服务，并保存链接；而且被拒绝的是整条消息，不是某个链接。
- **把链接放进按钮**：一条消息的按钮也有上限，按钮用于操作。

## 补充：旧的期望内容、永久错误与已结束事件的编辑上限

### 背景

CCHP 影子升级到 0ead2c9（2026-10-24 11:13Z 同步）之后，新渲染的消息都送达了：编辑 17 条、恢复 12 条、即时 2 条、外部上游汇总 1 条。但 `server.notify_messages` 里还剩 22 行旧代码渲染的期望内容：

- payload 14–25 KB，对应的事件都已恢复；
- `desired_at` 在 10-22 到 10-24 04:32Z 之间，`attempts` 已经 89–681 次。

同步只渲染还需要消息的事件（推送范围内、恢复后在保留期内），所以这 22 行永远不会按上面的 9000 字节预算重新渲染。editMessageText 每次都返回 400 `ENTITIES_TOO_LONG`，按"其他 4xx 5 分钟后重试"无限循环。`srenautix_notify_delivery_failures_total` 一直在涨，`ChannelDeliveryFailed` 持续成立，挡住了切换条件"Telegram 投递失败为 0"。

根因有两层：

- 期望内容没有记录由哪一版渲染器产出，渲染规则修好之后，没有途径换掉不再被同步的旧内容；
- 投递把"渠道拒绝这条内容本身"（永远不会成功）和临时拒绝混在一起，都每 5 分钟重试，没有终点。

### 决定

1. **记录渲染器版本，启动时重新渲染。**
   - `notify_messages.render_version` 记录产出期望内容的渲染器版本。常量是 `RENDER_VERSION`（`notify/channel.ts`），渲染规则变化时加一；旧代码写入的行为 NULL。
   - 进程启动后第一次同步之前，对期望与已呈现不同、没有放弃、版本旧于当前的行，按当前代码重新渲染期望内容。
   - 已恢复、超过保留期的事件也照样渲染，用已结束状态的模板（`MessageSource.byIds`，不论严重度、抑制与保留期）。风暴汇总按成员事件重新渲染；外部上游汇总按库中存的时间段统计重新渲染。
   - 事件、风暴或统计已经不存在的行保持原样，交给下面的永久错误处理。
2. **永久错误：先降级为纯文本，仍失败就放弃。**
   - 永久错误：
     - Telegram：400 中除了 message is not modified、要编辑的消息不存在或不可编辑、回调过期，以及群的问题（chat not found、没有发言权限、群已迁移）以外的错误，例如 `ENTITIES_TOO_LONG`、message is too long、can't parse entities；
     - 飞书：230001 请求参数无效、230025 消息内容超长、230099 卡片内容创建失败。
   - 遇到永久错误，用去掉实体的纯文本重试一次。Telegram 去掉 parse_mode 与全部标签，文字与 HTML 解析后的相同，保留键盘；飞书的卡片保留标题，正文的文字合成一个 plain_text，去掉按钮与表单（卡片只能更新为卡片）。
   - 纯文本送达时，这一版期望内容视为已呈现。纯文本仍是永久错误时，记 `abandoned_at` 与 `abandoned_reason`，这一版内容不再投递。
   - 放弃的内容不计入 `srenautix_notify_delivery_failures_total`，也不计入 `ChannelDeliveryFailed`；另记 `srenautix_notify_abandoned_total{channel, reason}` 与一条 error 日志。期望内容变化时清除放弃，重新尝试。
   - message is not modified 按已呈现处理。群的问题与 403 等其他拒绝仍然 5 分钟后重试并计入投递失败：这是配置问题，应当告警。
3. **已结束事件的编辑上限。**
   - `ended` 标记期望内容是已结束（恢复或合并）事件的消息。`ended_edits` 计事件结束后渠道作出应答的编辑次数，含被拒绝的，不含不可达与限流。
   - 达到 `MAX_ENDED_EDITS = 5` 之后，新的内容直接放弃（原因 `ended_edit_cap`），不再请求渠道。
   - 事件重新触发后计数清零。
4. **迁移只加列**（notify 轨道第 3 条，expand）：`render_version`、`ended`、`ended_edits`、`abandoned_at`、`abandoned_reason`，以及约束"放弃时间与原因同时有或同时没有"。N-1 版本照常运行，只是不认识放弃，继续重试。不涉及契约。

### 测试

- 集成测试用真实 PostgreSQL 和严格的 Bot API 模拟服务端：带 parse_mode=HTML 的请求按 `test/support/telegram-html.ts` 解析，实体序列化后超过 10000 字节返回 `ENTITIES_TOO_LONG`；编辑不存在的消息、内容没变也按 Bot API 应答。
- 一行旧代码写入的超长期望内容（没有新列、681 次尝试、事件已恢复且超过保留期）：模拟服务端与 Telegram 一样拒绝它；启动后被重新渲染为已恢复的模板，一次编辑成功。
- 永久 400 之后改为纯文本，文字与键盘不变；纯文本仍被拒绝时放弃，之后的同步、投递与重启都不再请求模拟服务端，内容变化后重新尝试。
- message is not modified 按成功处理；chat not found 照常重试并计入失败。
- 已结束事件编辑 5 次之后的内容放弃、不再请求；被拒绝的编辑同样计数。
- 单元测试覆盖两个渠道的错误分类，以及两种纯文本降级。

不采用的做法：

- **启动时删除旧行**：会丢掉渠道消息 id，事件再次触发时不能编辑原消息；而且旧内容未必都超限。
- **在同步里把保留期外的事件也渲染**：每 5 秒要渲染全部历史事件。旧内容只在渲染规则变化之后出现一次，启动时做一次就够了。
- **按尝试次数放弃**：临时故障（Telegram 不可达）也会累积次数。永久错误应当按错误的种类判断。
