# 0152 兜底模型路由：只在全部常规路由因故障域提前熔断时使用

## 背景

ADR 0080 的故障域提前熔断：事件涉及的组件落在某条路由的 `failure_domain` 内时，这条路由对本次研判视为打开；全部路由都被这样打开时阶段 B 跳过，只出阶段 A。常见部署里所有路由都经过同一个模型网关（自建的 API 网关、边缘代理、入口），它们的故障域相同。网关或边缘出事件时，全部路由一起被熔断，而这类事件对业务的影响往往最大，正好最需要阶段 B。

需要一条不经过这个故障域的路由，平时不用，只在这种时候用。它通常直连另一家服务方的 OpenAI 兼容接口，数据流向与保留条款都和常规路由不同，费用也单独结算，所以用量要单独记账并有每日上限。

## 决定

1. **路由属性 `role`**（契约 2.30.0，`ModelRoute.role`）：`regular` 为常规路由，不填时取这个值；`last_resort` 为兜底路由。配置里至少要有一条常规路由，只有兜底路由时 worker 拒绝启动。
2. **选择规则**：每次会话开始时确定路由组。
   - 配置了兜底路由、会话给出了兜底额度、并且全部常规路由都因事件涉及其故障域而提前熔断时，路由组是兜底路由；
   - 其余情况路由组是常规路由，兜底路由不参与选择、探测之外不收到任何请求。
   路由组内的选择与 ADR 0080 相同：先本档位再另一档位，修复阶梯、熔断、换路由都只在路由组内进行。兜底路由也可以声明自己的 `failure_domain`，事件涉及它时同样提前熔断。提示词按路由组中最小的上下文组装，常规研判的提示词不因配置了兜底路由而改变。
3. **真实调用失败不切到兜底路由**：常规路由因网络错误、超时、408、429、5xx 打开失败型或延迟型熔断，或者本次调用失败，研判照旧在常规路由之间切换，全部失败时只出阶段 A。理由：
   - 故障域熔断由事件本身决定：事件涉及网关，常规路由必然不可用，判断只依赖事件组件与配置，回放同一个事件得到同样的选择，可以审计；
   - 调用失败的熔断来自进程内的滑动窗口，原因多样：服务方限流、上游模型过载、单次超时。接到这里，兜底路由就成了日常的第三条路由，调用量随服务方的抖动变化，每日额度会被与网关无关的事件提前用完，网关真正出事时反而没有额度；
   - 兜底路由的出境范围因此可以预先说清：只有涉及常规路由故障域的事件会发往兜底服务方。
   网关已经失效、但还没有形成涉及它的事件时，这段时间里其他事件的研判因调用失败只出阶段 A；网关的告警进入后，涉及它的事件改用兜底路由研判。
4. **只用于事件研判**：会话的兜底额度由 worker 在事件研判开始时给出。主动优化的目标任务不给额度，全部常规路由熔断时照旧只出阶段 A，失败说明写明兜底路由只用于事件研判。评测把每条路由都当作常规路由单独评测（与 ADR 0110 清空故障域的做法相同）。
5. **用量与预算单独记账**：
   - 配置项 `budget.last_resort.daily_tokens` 是全部兜底路由合计每天（UTC）的上限，配置了兜底路由时必填，不填时配置校验失败；
   - 新表 `worker.daily_usage_last_resort (day, route_id, tokens, cost)` 按路由记录，研判结束时与 `daily_usage`、`daily_usage_purpose` 在同一个事务里写入；兜底路由的用量同时计入全部用途的当日合计，`budget.daily_tokens` 照样约束它；
   - 研判开始时读取当日已用；每次调用兜底路由之前检查"当日已用 + 本次会话已用 + 本次输入估算 + 本次输出上限"，超过上限时不发出请求，研判以 `budget_exhausted` 只出阶段 A，消息横幅写明兜底路由的当日用量与上限；
   - 同一时刻多个研判各自读取当日已用，超出上限的部分最多是并发研判数乘以单次研判的用量（单次研判的输入上限为 `per_research_input_tokens`）；
   - 指标：`srenautix_llm_budget_used_ratio{scope="last_resort"}`，截停计入 `srenautix_llm_budget_stops_total{reason="last_resort"}`。
6. **记录与标注**：
   - 研判清单的 `routes` 与 `worker.llm_calls` 照旧记录每个阶段、每次调用所用的路由；
   - 结论来自兜底路由时，研判输出带 `last_resort_route: {route_id, model}`（契约 2.30.0，`ResearchOutput.last_resort_route`），常规路由的结论不带这个字段；
   - 事件消息（Telegram、飞书卡片、issue 共用同一份消息结构）在"关键问题"的结论下面加一行：`由兜底线路研判：<路由 id>（<模型>），常规模型路由都依赖本事件涉及的组件`；
   - 研判的成本按路由组的币种记录；worker 的研判完成日志带 `last_resort`（使用的兜底路由）。
7. **OpenAI 兼容接口**：兜底路由用已有的 `api: chat_completions`。新增方言档案 `openai-compatible`：Chat 请求体的输出上限用 `max_tokens`（OpenAI 自己的 Chat 接口改用 `max_completion_tokens`，兼容接口的服务方普遍只认 `max_tokens`），结构化输出声明为 `json_object` 加提示词中的 schema，推理内容在 `reasoning_content`，上下文声明 128k；严格 `json_schema`、原生工具与上下文长度由启动时的能力探测实测覆盖（ADR 0080）。其余方言档案的请求体逐字不变。
8. **评测单条路由**：`srenautix eval` 与 `eval reconstruct` 增加 `--route <id>`（可重复），只评测列出的路由，只读取这些路由的密钥。兜底路由上线前用它在标注集上评测，与常规路由的成绩比较 top-1 与处置。

## 考虑过的方案

- **兜底路由也接管调用失败**：网关已坏但还没有事件涉及它的这段时间也能研判。代价见决定第 3 条：调用量与额度消耗取决于服务方的抖动，出境范围无法预先说清；网关出事时最先进入的通常就是网关自己的告警，这正是兜底路由要覆盖的事件。
- **把兜底路由当作普通的第三条路由排在最后**：不需要新属性，但平时任何一次调用失败都会落到它上面，与第 3 条的理由相同；也无法单独设每日上限。
- **按路由给每日上限**：多条兜底路由时各自一份额度更细，但兜底的用途是一个整体，按合计设上限更容易估计费用；按路由的用量照样记录在 `daily_usage_last_resort`。

## 结果

- 没有配置兜底路由时行为不变：用 20 份录制的研判记录（快照模式、真实模型响应）离线重算，研判输出、检查、token 用量与调用序列逐字段一致，发往模型的请求体逐字节一致。
- 单元测试：全部常规路由因故障域熔断时改用兜底路由、常规路由收不到请求；还有一条常规路由可用时不选兜底路由；常规路由连接失败时不切到兜底路由；没有兜底额度时（主动优化）只出阶段 A；当日额度不够时不发出请求；同一会话的用量累加；只有兜底路由的配置被拒绝；全部常规路由被出站策略禁用时只出阶段 A；`openai-compatible` 的请求体用 `max_tokens`；worker 配置要求 `budget.last_resort`；评测的 `--route` 只读取所选路由的密钥。
- 集成测试（真实 PostgreSQL 与 HTTP，三个 OpenAI 兼容的本地回放服务）：网关事件进入后两条常规路由收不到任何请求，兜底路由完成研判；研判输出带 `last_resort_route` 并符合契约，`daily_usage_last_resort` 记下与研判用量相等的一行，消息标注"由兜底线路研判"。
