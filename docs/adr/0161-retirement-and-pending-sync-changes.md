# 0161 退役与已合并、尚未同步的提交进入变更时间线；meta 告警的研判方向

## 背景

一段生产环境的并行运行里，三类结论与事实不符：

1. **计划内的退役没有关联到告警。** 一个存储组件按计划退役：先合并删除它全部定义的 Git 提交，几分钟后以 orphan 方式删除管理它的 Argo CD 应用，再删除三个 StatefulSet 与抓取配置。十分钟后"抓取 job 的目标全部消失"告警触发，实体是抓取 job（`Job:<job>`），不在拓扑里。变更时间线里没有这次退役：
   - 变更源（GitHub REST，ADR 0096）记录了这个提交，目标是 Argo 应用；告警落在抓取 job 上，与应用之间没有拓扑关系，按时间与依赖关系连不到它；
   - 从拓扑推导的发布（ADR 0104）只看新的 ReplicaSet、ControllerRevision 与版本标签变化，删除与缩到 0 不是发布；拓扑事件里被删除的 StatefulSet 还会被 informer 的重新列举补回来，看不出副本数；
   - 失败的一次性 Job（ADR 0140）与 SQL 审计表（ADR 0151）都不涉及。
   - 告警的组件是抓取 job，没有原因与变更时按症状成为根因，研判又在这个组件上提出"服务发现故障"。
2. **已合并、尚未同步的提交没有出现在应用漂移事件里。** 一个手动同步的 Argo 应用只按资源同步过，此后一直 OutOfSync，又合并了几个触及它的提交；24 小时后 ArgoCDManualAppDrift 触发。这些提交早已离开 30 分钟的变更窗口，事件只有告警与"应用未同步"的状态卡，没有指出哪些提交还没有同步。
3. **"副本多于负载需要"的告警被研判成资源紧张。** 告警报的是低负载下副本偏多，研判的结论却是连接池紧张、连接释放异常。告警目录把它改成 meta、实体改成逻辑组件之后，用同一批重建包重放：两次结论回到容量冗余，另一次（同一时段数据库故障，网关 5xx 很高）仍是"连接池耗尽导致 5xx"。证据卡各自的判定方向都对（副本规模卡在低负载时判为异常，连接池卡在占满时判为异常），模型不知道 meta 角色的含义，把同时段另一个故障的异常卡当成了这条告警的机制。ADR 0100 的条件方向表管的是各角色自身状态条件，与证据卡的判定无关。

## 决定

### 1. 退役变更（kind retire，契约 2.33.0）

工作负载被删除或副本缩到 0 并保持，是一次变更。server（`changes.kubernetes.retirements`，默认开启）与 eval 的重建用同一组查询与同一个 `deriveRetirements`（`changes/retire.ts`）：

- **数据**：kube-state-metrics 的 `kube_deployment_spec_replicas`、`kube_statefulset_replicas`、`kube_daemonset_status_desired_number_scheduled` 与 `up{pod!=""}`，区间查询，步长 60 秒，区间按步长对齐（change_id 与退役时刻在重算之间不变）。
- **判定**：一条副本数序列最后一次大于 0 之后还有取值（都是 0）时为缩到 0，退役时刻是第一个 0；之后没有取值、已经消失至少 5 分钟时为删除，退役时刻是最后一个大于 0 的点之后一个步长。kube-state-metrics 自己没有数据（全部副本数序列在最近两个步长内都没有点）时不推导删除。缩到 0 之后又恢复的不算。
- **合成**：`group_within` 内同一命名空间或同一个管理应用的退役合成一次变更。`targets` 是管理应用（拓扑中退役之前一小时内有效的 managed_by）与工作负载，`refs` 是管理应用；`change_id` 是 `kubernetes:<集群>:retire-<第一个工作负载与时刻的哈希>`。
- **`scrape_jobs`**：在退役之前一小时内出现过的目标 Pod 全部属于这次退役的工作负载（拓扑在退役之前两个步长时的属主），最后一个目标不晚于退役之后 5 分钟、到计算时刻已经消失的抓取 job。
- **`planned_by`**：退役之前 24 小时内最近一次触及这些工作负载、管理应用或管理应用的上层应用的变更源提交（不含运行时配置与推导出的变更），写进提交的 id、版本、时间、链接与说明。非空即为计划内的退役。
- **只删除抓取配置、工作负载仍在运行**的情况不推导：抓取配置对象与 `up` 的 job 标签之间的对应取决于抓取组件的命名规则，没有通用的依据。

### 2. 收敛与根因

- 告警在拓扑里没有对象锚点、`job` 标签在退役变更的 `scrape_jobs` 里、在退役之后的变更窗口内开始时，由这次退役解释（`retiredScrapeJob`），归到它所在的分组。有锚点的告警（例如 kube-state-metrics 导出的工作负载告警，job 是导出器）仍按拓扑关系判断。
- 没有锚点的告警按命名空间或 change 角色归到变更（ADR 0104 第 5 条）时跳过退役变更：同一命名空间里别的工作负载的告警与退役无关。
- 退役变更的根因候选是管理应用，没有管理应用时是工作负载。Git 合并与同步作用在应用上，工作负载是应用的一部分；候选只有应用时，根因不随拓扑里残留的哪个 StatefulSet 而变化。
- 研判中，事件里的退役变更是根因为它的候选的假设的支持证据（`Ledger.supportChanges`），与只有成员告警支持时相同，档位最高 likely（ADR 0122）。抓取 job 上的卡不在应用的范围内，没有这一条时计划内的退役在账本里得不到任何支持。

### 3. 已合并、尚未同步的提交（`pending_sync`，契约 2.33.0）

server（`changes.pending_sync`，默认开启，回看 72 小时）与 eval 的重建按 `argocd_app_info` 的 `sync_status` 找出最近两个步长内处于 OutOfSync 的应用，取它最后一个 Synced 样本的时刻；变更源的提交中触及这个应用、在这个时刻之前 3 分钟之后合并的（Argo CD 默认每 3 分钟比较一次 Git），标上 `pending_sync: [{application, out_of_sync_since}]`。一直没有 Synced 时取回看范围内的提交，`out_of_sync_since` 为 null。标注不写入变更源，事件引擎每次重算时并入输入，替换窗口内同一个提交。

- **列进事件，不归并**：告警落在提交标出的未同步应用本身上时，提交列进这条告警所在的分组（`AlertGroup.pendingChanges`），不受变更窗口与告警开始时间的限制，漂移的内容就是全部没有同步的提交。这种关系不把告警归并：一个提交常常触及很多应用，各应用的漂移不因此连成一个事件。
- **早于输入窗口的提交只按这种关系关联**：时间早于 `changeInputFrom` 的未同步提交不参与按时间的关联。重放按 pending 开始时刻接入告警，漂移告警的 pending 开始时刻可能紧挨着这个提交，按时间关联会把同一提交触及的几个应用的漂移连成一个事件，并把提交触及的其他应用排进候选。
- **候选**：只因未同步列进分组的提交，只让分组里落在它的未同步应用上的告警所在的应用成为候选。

### 4. 归属：变更来源

"已合并、尚未同步"放在变更来源这一层：

- **检测器（ADR 0105）**用来在没有告警规则时发现问题；漂移已经有告警规则（ArgoCDManualAppDrift、ArgoCDSyncFailed）并且触发了，缺的是原因，再合成一条告警只会重复；
- **卡片**是 PromQL 与 CEL，只能读指标：应用 OutOfSync 的状态已经由 argocd 领域包的状态卡判为异常，读不到 Git 里合并了哪些提交；
- **变更来源**同时知道 Git 合并了什么（变更源的提交）与集群同步到了哪里（Argo CD 的同步状态），"已合并、尚未同步"正是这两者之差，结果作为提交的属性进入事件的变更列表，阶段 A 的时间线、研判输入与通知都从这里取。

退役同样放在变更来源：它是集群状态的一次变化，解释的是随之出现的告警。

### 5. 阶段 A、研判输入与通知

- 阶段 A 时间线的变更行写上"计划内退役：<提交> <说明>"与"已合并、尚未同步到 <应用>（<时刻> 起 OutOfSync）"（`changes/notes.ts`）。
- 研判输入的变更段带上 `scrape_jobs`、`planned_by` 与 `pending_sync`，只在有时出现，其他事件的提示词不变。
- 通知中退役写成"计划内退役 <提交版本>"（没有计划依据时为"退役"），链接到计划依据的提交；未同步的提交标题后加"（已合并、尚未同步）"，现状与拓扑联系两段把它们合成一句"N 个已合并、尚未同步的提交 <版本>（最早的时刻）"。

### 6. meta 告警的研判方向

研判的系统提示词加上告警角色的含义：cause 报原因，symptom 报症状，change 报变更，forecast 报预测，meta 报观测缺口或容量冗余，本身不是故障。假设的机制要与成员告警报告的状况方向一致：告警报副本偏多、负载偏低、资源富余时，资源紧张、连接耗尽、容量不足这类机制与它相反。hypothesize 要求成员告警全部是 meta 时每个假设都解释这些告警报告的状况；conclude 不选只解释同一时段另一个故障的假设，那个故障写进 situation 或 investigation 类的修复建议。

## 结果

- 计划内的退役成为抓取 job 消失告警的头号候选（管理应用，来源 change），事件的变更里带着退役、带走的抓取 job 与计划依据的提交；研判的账本里这个候选有支持证据。
- 应用漂移事件列出全部已合并、尚未同步的提交与 OutOfSync 的起点，提交触及的其他应用不进入候选，各应用的漂移仍各自成事件。
- 早于这两类序列导出的重建包、没有 kube-state-metrics 或 Argo CD 指标的集群，结果与之前相同。
- 退役推导每分钟读四组区间序列（区间按分钟对齐，缓存一分钟），未同步推导每 5 分钟读一组 72 小时的区间序列（漂移告警本身要持续很久才触发）；查询在证据数据源上执行。
- 所有事件的研判提示词多了告警角色一段，请求体与之前的录制不同；离线重算复用录下的响应，输出不受影响，真实调用的结论变化由评测度量。
