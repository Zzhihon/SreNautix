# 0195 事件的认领：谁在处理

## 背景

多人值班时，控制台与消息都看不出谁在处理哪个事件。两个人可能同时处理同一个事件，也可能都以为对方在处理。

## 决定

1. 事件可以被认领。认领人成为处理人；已有处理人时认领就是接手。处理人可以放下，事件回到没有处理人的状态。
2. 新权限 `claim`（契约 2.59.0），授予 responder、approver、admin（合规配置的 sys-admin 继承 approver）。有这个权限的人都可以认领、接手与放下，不要求是当前处理人：值班交接时由接手的人操作。
3. 存储：`server.incident_claim_events` 只追加，每条记录动作（claim 或 release）、主体、渠道与时间。当前处理人是每个事件最近一条记录为 claim 时的主体。没有处理人时放下不做事，也不记录。
4. 接口：`POST /v1/incidents/{ref}/claim` 认领（返回当前处理人），`DELETE /v1/incidents/{ref}/claim` 放下。事件摘要与事件详情带 `claim`（没有处理人时为 null）。
5. 认领与放下都进入事件时间线，种类为 `claim`。
6. 控制台：收件箱的一行显示处理人；事件详情的结论下面显示处理人，有 `claim` 权限时提供"我来处理"、"接手"与"放下"。Grafana 插件只显示处理人。
7. 事件恢复后处理人保留，作为记录。
8. 聊天渠道（契约 2.60.0）：Telegram 与飞书的事件消息在事件未恢复且没有处理人时带"我来处理"按钮（按钮种类 `claim`）。点击的账号必须已用 `/link` 绑定到控制台主体，权限按这个主体的角色绑定判断，与控制台的接口相同；认领记录的渠道是 telegram 或 feishu。有处理人后，消息的现状段写"处理人 · 主体"，不再带按钮；接手与放下在控制台操作。

## 考虑过的方案

| 方案 | 不采用的原因 |
|---|---|
| 只允许处理人放下 | 交接时原处理人可能已经下线，接手的人无法放下或接手 |
| 用一张表存当前处理人 | 失去历史；时间线要的正是每一次认领与放下 |
| 认领绑定 Alertmanager 的 silence | 认领是"谁在处理"，不是"不再告警"；两者混在一起会让人误以为认领会静默告警 |

## 结果

- 值班人在手机上收到消息后可以直接认领，其他人在同一条消息里看到处理人，不需要打开控制台。
- 聊天里只能认领，不能接手：接手会覆盖别人的认领，留在能看到完整时间线的控制台里做。
