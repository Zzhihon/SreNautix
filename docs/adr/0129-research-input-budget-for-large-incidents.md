# 0129 大事件的单次研判输入：估算校准与拓扑写法

## 背景

CCHP 影子上，检测器开出的 PDB 事件有 4 次研判因单次研判的输入上限停止（约 15.1 万，上限 15 万 token），primary 路由的调用因"超过上下文"被跳过（Zzhihon/SreNautix#6）。研判的输入在发送前按路由估算（ADR 0082、0099）：原始估算（有分词器时数 token，否则按字节）乘以校准系数。校准系数是"实际 usage ÷ 原始估算"的指数加权平均与最近最大值中的较大者，最近最大值每个样本只回落 2%。

重建评测的研判记录（trace-7ff3e72，CCHP 的两条路由）里，primary 有一次原始估算约 2.9k token 的请求，服务方报告的输入是 24,993 token；同样的请求下一次报告 2,877。这一个样本把最近最大值抬到约 8.7，之后 primary 的估算长期是实际的 5 到 9 倍：一次实际输入 18,809 token 的 hypothesize 估算为 94,871。估算偏大之后，裁剪按偏大的数裁（ADR 0099），研判合计按偏大的数截停，路由窗口按偏大的数判断"超过上下文"。

ADR 0127 之后，提示词里最大的部分是拓扑子图：研判子图有几百个 Pod 时，逐个列出的 Pod、ReplicaSet 与它们的边占提示词的大半。

## 决定

1. **异常的 usage 不计入校准**：一次调用的"实际 usage ÷ 原始估算"在 [0.2, 3] 之外（`CALIBRATION_RATIO_RANGE`）时不更新校准，记指标 `srenautix_llm_calibration_rejected_total{route}` 与一条 warn 日志。正常的差别在这个范围之内：字节估算对中文与英文约为 0.4 到 0.7，有分词器时接近 1。这次调用的 usage 照常计入研判与当日的用量。
2. **状态库里系数异常的校准从头开始**：worker 启动时读回的路由校准，系数或最近最大值在范围之外时（之前计入过异常样本），按未校准处理（`restoredCalibration`）。升级后 CCHP 的 primary 不再沿用被撑大的系数。
3. **拓扑按组件粒度写**（`topologyView`）：由控制器拥有、自身与事件无关的对象（不是根因、候选或事件组件，没有告警，不是证据卡的实体）不逐个列出，按 kind 计数记在顶层属主的 `owns` 上；它们的其他边（例如 Pod 所在的节点、挂载的卷）改记在属主上，去重，置信度取最高。与事件有关的 Pod 照常列出。按跳数的裁剪（ADR 0099）作用在这个写法上。
4. **单次研判的上限不分档**：ADR 0127 与本决定之后，CCHP 发布事故规模的事件（133 张卡、880 个节点的子图、23 条成员告警、20 项卡片检查）每次调用的输入约 2.4 万 token，不用裁剪；输入最多的路径（hypothesize 走满 3 轮再结论）按最大的一次计约 9.8 万，在 15 万之内。上限保持 15 万，按事件规模分档没有必要。

## 结果

- 实现在 `apps/srenautix/src/llm/budget.ts`（`plausibleRatio`、`restoredCalibration`）、`llm/routes.ts`、`llm/session.ts` 与 `research/prompt.ts`（`topologyView`）；契约不变。
- 单元测试：24,993 对 2,877 的样本不改变校准，读回的被撑大的校准从头开始；拓扑里无关的 Pod 与 ReplicaSet 计入属主，它们到节点的边合并为属主的一条边。
- 集成测试（录制回放的模型、primary 的路由写法与默认预算）：上面规模的事件，每次调用都在阶段单次上限之内且不用裁剪，最多轮数时也在研判上限之内，研判不以预算停止。
