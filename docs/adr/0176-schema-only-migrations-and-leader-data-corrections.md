# 0176 迁移只改 schema，语义修正在取得主实例之后执行

## 背景

server 启动时执行扩展迁移（ADR 0040），之后才参与选主。滚动升级时，新版本的进程完成迁移的那一刻，旧版本的实例通常仍持有主实例租约，事件引擎与通知引擎仍按旧版本的语义读写状态库，直到旧 Pod 退出、租约过期、新实例取得租约。

ADR 0173 的 `notify` 迁移 4 除了加列，还清除了库里已有的 `ended_edit_cap` 放弃，让这些消息在新版本启动后得到一次最后一次编辑。从 ADR 0173 之前的版本升级时：迁移完成不到一秒，仍是主实例的旧 server 同步到同一条已结束事件的消息，按旧规则（编辑次数用完时不请求渠道、直接放弃）再次把它标为 `ended_edit_cap`；新 server 成为主实例后按新规则保留这种放弃，消息停在旧内容，`NotifyAbandoned` 条件成立约 1 小时并触发自身告警。

原因：迁移改动的行属于旧版本仍在写的数据，迁移随即被旧代码按旧语义写回。只改 schema 的迁移没有这个问题：N-1 版本不认识新列，也就不会改写它们。

## 决定

### 1. 迁移只改 schema

扩展迁移只增加表、列、索引与放宽约束，不改写已有的行。按新语义修正已有数据是数据修正，单独登记，不放在迁移里。`notify` 迁移 4 只加 `final_edited_at` 列，清除 `ended_edit_cap` 的语句移到数据修正 `notify/ended-edit-cap-final-edit`。

### 2. 数据修正在取得主实例之后执行一次

- 登记：每个修正有全局唯一的名字（`<模块>/<说明>`）与一个在事务里执行、返回改动行数的函数（`store/corrections.ts` 的 `Correction`）；server 的修正列在 `roles/server-schema.ts` 的 `serverCorrections`，按列出的顺序执行。
- 记录：`store` 迁移 2 建 `server.data_corrections`（名字、执行时间、执行的实例、改动行数）。执行前取这个名字的咨询锁并检查记录，已记录的跳过；执行与记录在同一个事务里，失败时都不生效。
- 时机：server 的主实例身份由 `afterCorrections` 包装：内层（Lease 或单实例）取得主实例之后先执行全部还没有执行过的修正，完成之后 `isLeader` 才为 true、`acquired` 才 resolve。事件流水线、通知同步与投递、Telegram 更新、自愈 PR 等单活工作都按这个身份运行，因此在修正之前不会读写这些数据。新实例取得租约时，旧实例已经失去租约（Lease 过期之前新实例取不到），不再写入。
- 失败：修正抛出时记 error 日志，仍是主实例时每 30 秒重试，期间单活工作暂停。修正不跳过：跳过会让数据停在旧语义，失败的原因要修复。
- 只执行一次：之后的重启、主实例切换、其他副本取得主实例都不再执行。

### 3. 修正只改旧语义写下的行

修正执行时，库里可能已经有本版本写下的同类数据（例如本版本已经运行过一段时间、记录被清除后重新执行），修正的条件要区分新旧语义，只改旧版本写下的行。`notify/ended-edit-cap-final-edit`：本版本的 `ended_edit_cap` 是最后一次编辑被渠道拒绝，放弃时写一条终态记录（`incident_reasons`，stage `notify`、code `ended_edit_cap`，once 键为 `<消息 id>:<期望内容哈希>`，ADR 0172）；ADR 0173 之前的版本放弃时不写终态记录。修正只清除没有这条记录、也没有 `final_edited_at` 的放弃，并让它立即进入待投递。清除本版本的放弃会让被拒绝的编辑再请求一次、再放弃一次，`NotifyAbandoned` 再成立一次。

### 4. 主实例切换时立即停止写入

通知引擎的同步与投递在写每个渠道目标的期望内容、投递每条消息之前检查主实例身份（`EngineOptions.isLeader`），一轮进行到一半时失去租约也立即停止，不等这一轮结束。Telegram webhook 在成为主实例（含数据修正完成）之后注册。

## 考虑过的方案

- **迁移在取得主实例之后执行**：readyz 依赖扩展迁移完成（ADR 0102），新 Pod 在取得租约之前不能就绪，滚动升级的新 Pod 永远等不到旧 Pod 退出；N-1 兼容的扩展迁移本身也不需要等。
- **迁移里清除，新版本再按新规则清除一次**：旧实例在两次清除之间写回的行仍被保留，第二次清除的时机同样需要"取得主实例之后"，等于本决定加一条多余的迁移语句。
- **按原因的文字区分新旧放弃**：旧版本的说明是"事件结束后已编辑 N 次"，文字随版本变化；终态记录是 ADR 0172 之后的契约，判断依据稳定。

## 测试

- 集成（`test/integration/leader-corrections.test.ts`，真实 PostgreSQL 与 envtest 的 Kubernetes Lease）：库先在 ADR 0173 之前的 schema 上，已结束事件的消息编辑满上限、按旧规则放弃；旧实例取得租约；新实例执行迁移（这条放弃不变），参与选主但取不到租约，期间同步与投递不写库、不请求渠道；旧实例在迁移之后再次按旧规则放弃同一条消息；旧实例退出、租约过期，新实例取得租约后执行修正（记录执行的实例与行数），同步与投递发出最后一次编辑（精简内容与停止更新的说明），记 `final_edited_at` 与终态记录 `final_edit`，之后不再请求渠道；修正已记录时不再执行；本版本写下的、带终态记录的放弃不清除；修正失败时主实例身份保持为 false，失败原因修复后重试成功。

## 结果

- 迁移：`store` 轨道版本 2（`server.data_corrections`）；`notify` 迁移 4 只加列。都只加表与列，N-1 版本照常运行。
- 实现：`store/corrections.ts`（`runCorrections`、`afterCorrections`）、`notify/corrections.ts`、`roles/server-schema.ts`（`serverCorrections`）、`roles/server.ts`（主实例身份经 `afterCorrections` 包装，Lease 的持有者身份取 Pod 名）、`notify/engine.ts`（`isLeader` 检查）、`notify/index.ts`（webhook 在成为主实例之后注册）。
- 以后的迁移遵循：迁移只改 schema；需要按新语义改写已有数据时写一个数据修正，条件只匹配旧版本写下的行。
