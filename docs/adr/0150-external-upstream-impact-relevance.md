# 0150 外部上游事件的业务影响按相关性判定

## 背景

ADR 0147 让根因是外部上游的事件进入每小时汇总，同时有业务影响时照常即时推送。业务影响按集群判定：同一集群里只要有一条满足 `business_impact.alert_labels` 的告警在触发，全部外部上游事件都即时推送，横幅写“上游故障已影响业务”。

一个部署里，SLO 工单类的 L0 warning（错误预算慢速消耗）从前一天起一直在触发。此后每一个上游服务方的事件都被即时推送并标成“已影响业务”，每小时汇总里每个上游都写着“波及业务，已即时推送”，汇总失去了意义（Zzhihon/SreNautix#16）。运维侧把条件收窄到 `severity: critical` 只是绕开了这次的告警：任何一条长期触发的 critical 业务告警仍会让全部上游事件即时推送。

## 决定

业务影响按每个外部上游事件分别判定，信号满足下面任一条才算与这个上游事件相关：

1. **本事件的影响卡**：本事件异常的影响卡（`impact: true`）总是相关。
2. **时间窗**：业务告警，或其他非外部上游的触发中事件（其中异常的影响卡），在上游事件开始（`first_firing_at`）之后 `business_impact.within`（默认 30 分钟）之内开始。开始时间早于上游事件的不算：它在上游出问题之前就已经存在，不是这个上游造成的。
3. **拓扑路径**：业务告警的组件（`alert_state.component`），或影响卡所在事件的根因，沿依赖边在 `business_impact.topology_hops`（默认 6 跳）以内到达上游根因。方向与根因排序相同（from 依赖 to，故障沿边反向传播），展开规则与 `TopologyGraph.reach` 相同：起点是组件及其全部成员；枢纽可以被到达但不再展开；经访问边（`egress_to`）到达的组件不再沿它的依赖展开；命名推断的边只用于展示，不算。路径在上游根因 `topology_hops` 跳以内的子图（`TopologyStore.subgraph`，ADR 0144）上查找，结果缓存 60 秒。信号的组件与上游根因属于同一个组件时直接相关。`topology_hops: 0` 时不按拓扑判定。

只来自告警、不在拓扑里的上游（模型服务方 provider）没有路径，只按时间窗判定；拓扑里有的外部依赖（ExternalName Service、经服务图出现的外部服务）两条都适用，业务告警开始得再晚，只要它的组件依赖这个上游也算相关。

**依据写进消息**：

- 事件横幅：`上游故障已影响业务：CCHPErrorBudgetBurnFast（在上游事件开始后 21 分钟开始）`，拓扑的写成 `（拓扑路径 Deployment:shop/checkout → payments）`，本事件的卡写 `（本事件的影响卡）`，其他事件的卡写 `（所在事件在上游事件开始后 N 分钟开始）`。组件用可读名称，没有时用组件键。
- 每小时汇总的业务影响一行：每个业务告警与影响卡写明相关的是哪个上游与依据，例如 `CCHPErrorBudgetBurnFast（10:52 起，未恢复；在上游 柚子 的事件开始后 21 分钟开始）`。同一时段里一条告警与多个上游事件相关时，取开始最早的那个上游事件。没有相关信号时写 `业务影响：无（与上游事件相关的业务告警 layer=L0 0 条，相关的影响卡无异常）`。
- 每个上游一行的“波及业务，已即时推送”只出现在有相关业务影响的上游上。

issue 的判定（`externalState`）用同一个分类：上游事件有相关的业务影响时照常开 issue。

配置（`notify.digest.external_roots.business_impact`）：

```yaml
business_impact:
  alert_labels: { layer: [L0] }
  impact_cards: true
  within: 30m
  topology_hops: 6
```

chart 的 `notifyDigest.externalRoots.businessImpact` 增加 `within` 与 `topologyHops`。

默认值的取舍：

- `within` 30 分钟：上游故障通常在几分钟内经网关反映到边缘的错误率；错误预算的快速消耗告警的评估窗口与 `for` 加起来在 15 分钟以内。30 分钟留出一倍余量，同时让一小时汇总里先后出现的不同上游可以分开。
- `topology_hops` 6：对象级的依赖链（工作负载 → Pod → Service → 后端 Pod → 外部 Service）在 5 跳左右，取 6。

## 不采用的做法

- **只按告警的 severity 收窄**：critical 的业务告警同样可能长期触发，问题没有消失。
- **按上游事件仍在触发期间的任何业务告警**：上游事件持续数小时时，期间无关的业务告警都会算进去，与按集群判定的结果相差无几。
- **允许业务告警略早于上游事件**：上游事件的开始取成员告警最早的开始，业务告警早于它说明业务问题先出现；需要这类关联的部署，业务组件依赖上游时由拓扑路径覆盖。

## 测试

- 单元（`test/unit/notify-signals.test.ts`）：依赖路径经成员与服务到达上游、跳数不够时不算、枢纽与访问边之后不展开、命名推断的边不算、方向相反时不算；横幅里四种依据的中英文；汇总的业务影响一行带相关的上游与依据。
- 集成（`test/integration/notify-external-digest.test.ts`，真实 PostgreSQL）：
  - 10:52 开始的 L0 告警只让 10:31 与 10:40 开始的上游事件即时推送，横幅写明“在上游事件开始后 21 分钟开始”“12 分钟”；10:05 开始的 Kimi 留在汇总里，issue 判定为不开；汇总写明告警与“柚子”的事件相关；
  - 从前一天起一直触发的 L0 warning 不让任何上游事件即时推送，汇总写明没有相关的业务告警；
  - 拓扑里 checkout 的 Pod 经服务图调用外部的 payments-api：checkout 的 L0 告警在 payments 事件开始 50 分钟后才开始，仍按拓扑路径即时推送，横幅与汇总写明路径；同一时段不在拓扑里的 Kimi 不受影响。
