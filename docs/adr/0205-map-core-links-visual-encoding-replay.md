# 0205 地图的核心链路、视觉编码与时间回放

状态：已采纳

## 背景

全集群地图（ADR 0199）上线后，参考部署（CCHP）2026-11-14 的地图有 117 个组件、664 条边：

| 边 | 条数 |
|---|---|
| 网络策略推出、低于 τ（0.5） | 545 |
| 网络策略推出、等于 τ（0.6） | 20 |
| 配置引用（0.7） | 85 |
| 领域包声明（1） | 12 |
| 路由入口 | 2 |

"全部依赖"开关画出全部 664 条，指向或选中组件时也画出它的全部边，包括只被网络策略放行的边。不低于 τ 的 119 条里，大部分是业务组件与运维组件向 vmsingle（7 个服务）、vmalert、Loki、Tempo、OTel Collector 上报。值班的人要找的"请求从哪里进来、经过谁、落到哪个数据库"被这些线盖住。

组件只有状态色（根因、受影响），入口、常驻服务、数据库、一次性任务看起来一样；边全是同一种灰线。

ADR 0199 推迟了时间滑块：地图只回答"现在"，复盘时看不到事件在哪个时刻落在哪里、传播到哪里。拓扑历史已经按时间点可查（ADR 0144，保留 `topology.history_retention` = 14 天），`/v1/topology/map` 已经接受 `at`。

## 决定

### 1. 边分三档（`classifyEdges`，`packages/ui/src/domain/cluster-map-model.ts`）

| 档位 | 画出的边 |
|---|---|
| 核心链路（默认） | 领域包声明的依赖、路由入口，以及从核心、支撑领域出发，不指向运维自身（`self`）领域与共享汇，置信度不低于 0.7 的配置引用；再做传递约简 |
| 全部依赖 | 置信度不低于 τ 的边 |
| 网络放行 | 再加上低于 τ、只被网络策略放行的边 |

- 共享汇：被至少 `SINK_MIN_SERVICES`（4）个服务依赖的组件。指向它的配置引用不进核心链路；组件名称旁写"← 服务数"。
- 传递约简：A 经别的核心边能到达 C 时，A → C 降到"全部依赖"。声明的边与入口不约简。
- 网络策略推出的边不进核心链路：它只说明流量被放行。
- 领域包没有声明业务领域时不按档次筛选，只按共享汇与约简。
- 事件的传播路径（两端都是根因或受影响的组件，置信度不低于 0.7）在任何档位都画出。
- 指向或选中组件时画出它不低于 τ 的边；只被网络策略放行的边只在"网络放行"档画出。

### 2. 视觉编码

| 对象 | 编码 |
|---|---|
| 组件的角色 | 左侧色条与副标题：入口（series-7 紫）、服务（series-1 蓝）、数据（series-3 绿）、任务（series-5 粉）、静态 Pod（faint 灰） |
| 领域的档次 | 标题前的标签（核心、支撑、底座、运维自身）；核心领域的框用 info-soft 底色 |
| 边的种类 | 声明的依赖蓝色实线，路由入口紫色实线，配置引用灰色实线，网络策略放行灰色细点线 |
| 状态 | 不变：根因红或橙的边框与底色，受影响橙色底色，传播路径橙色虚线 |

- 角色不用红、橙：它们留给状态。色条与状态互不覆盖，一个组件同时读得出"是数据库"和"是根因"。
- 角色（`componentRole`）：有路由出边的是入口；Job、CronJob、Workflow 是任务；静态 Pod 按类型；有状态（StatefulSet 或持久卷）而且除共享汇外不依赖别的组件的是数据；其余是服务。参考部署的网关是带临时卷的 StatefulSet，它依赖数据库，所以是服务。
- 边按两个组件中心的相对位置选择出入的一侧（左右或上下）。同一列上下排着的组件之间的边不再从右侧绕出、再折回左侧。

### 3. 时间回放

- 新接口 `GET /v1/topology/map/timeline?cluster_id&from&to`（契约 2.66.0）：区间里触发过的事件与触发区间，过滤与地图相同（没有合并、没有被抑制、调用方读取作用域内）。区间不超过 7 天，最多 2000 个事件，超出时 `truncated`。
- 控制台地图上方加时间轴（`MapReplay`）：最近 24 小时切成 15 分钟一格。直方图是每格结束时仍在触发的事件数，严重与其余分开叠放。上方一行标出这一格里新触发的事件：长期不恢复的事件让直方图几乎是平的，新触发的时刻才值得回放。
- 拖动滑块、点直方图或逐格播放（每格 1.2 秒）选出时刻。地图按这个时刻取 `/v1/topology/map?at`，事件的落点与传播照常计算；最右一格回到"现在"。
- 时刻写进 URL（`/topology?view=map&at=`），可以分享。时刻对齐到格子边界。回放时地图不轮询，换时刻时保留上一刻的地图直到新的取到。

## 考虑过的方案

- **服务端给边打档位**：档位依赖领域的档次与画布上的合并，是展示规则。放在 UI 的纯函数里，可以单测，不改契约。
- **按扇入的组件数认定共享汇**：参考部署 17 个 Workflow 都指向 vmalert，按组件数会把发布流水线里的引用算成"很多服务"。按服务数计。
- **把 PostgreSQL、Dragonfly 这类被多个服务依赖的组件排除在核心链路之外**：参考部署上它们由领域包声明，声明的边不受共享汇影响，正是业务链路。
- **回放时间轴取每一刻的完整地图**：24 小时 96 格，每格一次地图请求。时间轴只取事件区间，地图按需取。
- **布局随时间保持不变**：组件在不同时刻会出现、消失（Workflow 每次一个），取并集会画出当时不存在的组件。每一刻按当时的结构排布，排布是确定的。

## 结果

参考部署 2026-11-14 的地图：

| 档位 | 画布上的边（合并同类组件后） |
|---|---|
| 核心链路 | 14：`cchp` 入口 → gateway、control；gateway、control、worker、archive-exporter → cchp-postgres、dragonfly、cchp-nats |
| 全部依赖 | 97 |
| 网络放行 | 628 |

- 角色：入口 1、服务 67、数据 10、任务 12、静态 Pod 6。数据是三个 CNPG 集群、Dragonfly、NATS、vmsingle、vmalertmanager、Loki、Tempo、SreNautix 的 MinIO。
- 线上服务端（4249874）按时刻取地图，过去 24 小时 7 个时刻：56–537 毫秒，中位 86 毫秒。不同时刻的组件数 117–127，同时触发的事件 22–33 个。
- 截图用真实数据在本地渲染，包含生产节点名，不放进仓库。
