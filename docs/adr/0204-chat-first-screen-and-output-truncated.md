# 0204 聊天消息的首屏只有五行；模型输出被截断单独记为失败原因

状态：已采纳

## 背景

参考部署（CCHP）2026-11-12 19:06Z 到 11-13 03:30Z 的研判全部以“模型输出无效”结束，Telegram 写“处置：无法判定。证据不足以给出处理或忽略”。原因有两层：

1. glm-5.3 默认开启思考，推理计入 `max_tokens`。这段时间的 59 次研判调用每次都用满阶段输出上限（hypothesize 6000），正文为空，`finish_reason` 为 `length`。路由加 `thinking: disabled` 后，同一请求回放以 `stop` 结束（cchp-k8s-ops#617）。
2. 结构化调用把截断与“不是 JSON、不符合 schema”记成同一个原因 `model_output_invalid`。消息只能写“模型输出无效”，值班人看不出是输出上限的问题。

同一条 Telegram 消息的首屏有 7 行：标题、状态与事件标签、首次触发、横幅（研判状态）、处置、影响、下一步。处置为“无法判定”时，处置行与其原因不给值班人任何可执行的信息；事件标签只用于检索。首屏之后是全部段落，平铺展开。

## 决定

### 1. 失败原因 `output_truncated`（契约 2.65.0）

- 一次结构化调用的全部无效输出都因达到输出上限而结束（Chat 与 Messages 接口的 `length`，Responses 接口的 `max_output_tokens`）时，原因为 `model_output_truncated`，研判失败类型为 `output_truncated`，文字“模型输出达到输出上限被截断”。
- 只要有一次无效输出不是截断（不是 JSON、不符合 schema、拒绝、内容过滤），原因仍为 `model_output_invalid`。
- `output_truncated` 与 `invalid_output` 的处理相同：停止原因为模型不可用，模型恢复后重新研判，评测计为结构化失败。

### 2. 结论块是三行：结论、影响、下一步

取代 ADR 0194 第 1、2 条。`NotifyMessage.brief` 的三行：

- **结论**：有模型结论时写结论等级与根因，用了兜底路由时注明；只有规则结论时写规则判定的根因；否则写研判的状态（研判中、模型研判失败、没有模型研判，粗体）、原因与阶段 A 的候选根因，例如“结论：**模型研判失败** · 模型输出达到输出上限被截断 · 候选根因 `gateway`”。原因的文字自身可能带括号，所以用“ · ”接在状态之后。处置不是“无法判定”时在行尾写处置。
- **影响**：最多 3 项。影响面上异常的卡在前，其次是异常的业务关键信号。只列有主值与阈值的卡，每种检查一项，写成“对象 卡片标题 数值（阈值 x）”。接近阈值的正常卡、没有阈值的卡与告警条件卡（`card_id` 以 `/condition` 结尾）留在详情里。
- **下一步**：第一个提议；没有提议时为第一条修复建议（模型写的标注【模型】）；都没有时为 runbook。

研判状态不再写在横幅。横幅只写阶段 A 未生成、状态库降级、观测盲区与上游影响。处置的原因留在关键问题段。

### 3. Telegram 的首屏与折叠

- 首屏最多 5 行：标题；状态行；结论、影响、下一步。
- 状态行：未恢复时为“未恢复 · 首次触发 时刻”，恢复后为“已恢复 · 开始 → 结束（时长）”。事件风暴与横幅接在同一行后面。状态行只取事件自身的时刻，不依赖渲染时的当前时间。飞书的副标题用同一个函数。
- 事件标签与全部段落放在同一个 `<blockquote expandable>` 里：`buildHtml` 把相邻的折叠段合成一个引用块，只占一个结构实体。段标题在引用块里加粗。最近操作与控制台链接在引用块之后。
- Telegram 不允许引用块嵌套，折叠块里的证据原文按普通文字输出，前一行的“来源：”标明出处。不可信原文仍然不产生任何格式实体。
- 测试：报告黄金文件与渲染黄金用例的首屏不超过 5 行，第三行起依次是结论、影响、下一步；研判失败、事件风暴与恢复同时出现时仍不超过 5 行。

## 考虑过的方案

| 方案 | 不采用的原因 |
|---|---|
| 首屏之后各段分别折叠 | 每段一个引用块，展开前仍有 7 个段标题；每个引用块占一个结构实体 |
| 截断也记为 `model_output_invalid`，在说明里写 `finish_reason` | 消息只写原因码的文字，值班人看不到说明 |
| 处置为“无法判定”时照写处置行 | 这一行不给出可执行的信息，原因已在关键问题段 |
| 影响行沿用业务关键信号段的第一项 | 第一项可能是接近阈值的正常卡或没有阈值的计数卡，首屏读者会当成影响 |

## 结果

- 参考部署的三个报告黄金用例在 Telegram 的首屏为 5 行，其余内容折叠。之前头部为 6 到 7 行，之后平铺全部段落。
- 截断导致的研判失败在 Telegram 的结论行写“模型研判失败 · 模型输出达到输出上限被截断”。cchp-k8s-ops#617 之前那一类事件能直接看出原因。
- GitHub issue 与飞书使用同一个结论块，同样换成三行；它们不使用 Telegram 的折叠块，处置行与原因照常在关键问题段。
