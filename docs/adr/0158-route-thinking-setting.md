# 0158 路由的思考模式设置

## 背景

兜底路由（ADR 0152）通常直连一家服务方的 OpenAI 兼容 Chat 接口（`dialect_profile: openai-compatible`）。有的服务方默认开启思考模式：模型先输出推理内容（`reasoning_content`），再输出正文，推理 token 计入 `max_tokens`。

研判各阶段的输出上限按正文的大小设定（hypothesize 6000、conclude 8000）。默认思考的服务方在大段提示词上先推理到上限，正文为空，`finish_reason` 为 `length`；修复阶梯重新请求得到同样的结果，研判以 `invalid_output` 失败。用一家默认思考的服务方在标注集上实测：每个用例的 hypothesize 两次调用都输出 6000 个推理 token、没有正文，研判全部失败。

这类服务方在 Chat 请求体里提供关闭思考模式的字段 `thinking: {"type": "disabled"}`，这个字段不在 OpenAI 的 Chat 协议里。

## 决定

1. **路由设置 `thinking`**（worker 配置与评测配置，`llm.routes[].thinking`）：取值只有 `disabled`，不填时请求体与之前逐字段相同。设置后这条路由的每个 Chat 请求体都带 `thinking: {"type": "disabled"}`：研判调用、修复阶梯的重新请求、启动时与评测开跑前的能力探测都带，探测测到的是研判时的行为。
2. **只用于 Chat 接口**：`api: responses` 的路由设置 `thinking` 时构造路由运行时直接失败（worker 启动失败，评测不开跑）。
3. **不进入契约**：`thinking` 与 `timeouts`、`model_class` 相同，是部署配置，与研判输出、事件、控制台无关；契约的 `ModelRoute` 不变。
4. **阶段的输出上限不变**：上限约束的是每个阶段的正文大小和每日预算的估算，推理放在上限之内会让同一个阶段在不同服务方上的正文空间相差数倍。需要推理的路由用默认不思考、或推理很短的模型。

## 考虑过的方案

- **按服务方的思考模式放大输出上限**：推理长度随提示词变化，实测一次 hypothesize 推理超过 6000 token 仍没有结束，上限要放大到数万才稳定，每次研判的用量与兜底路由的每日上限都要跟着放大，费用与耗时不可预期。
- **在 `openai-compatible` 方言档案里固定带 `thinking` 字段**：同一档案覆盖多家兼容接口，关闭思考的字段名各家不同，不认识的字段有的服务方会拒绝请求。按路由配置，只发给确认支持的服务方。
- **通用的请求体附加字段**：任意字段都能透传，但出站模块要对每个请求体做的检查（ADR 0081）多了一个不受控的入口；需要的只有这一个开关。

## 结果

- 单元测试：`thinking: disabled` 的路由在研判调用与能力探测的每个 Chat 请求体中都带 `thinking` 字段；不设置时请求体与之前相同；worker 配置只接受 `disabled`；评测配置把它单独给出、不写进路由对象；`api: responses` 的路由设置它时构造失败。
- 用这家服务方在同一标注集上重新评测，研判全部完成（成绩单只保存在部署方本地）。
