# 0032 声明式证据查询的执行与限制

## 背景

证据卡的查询来自领域包（DESIGN §6.1）。多集群安装时，中心通过 reader 查询分支集群的指标后端。reader 持有本集群数据源的只读凭证，如果它执行中心发来的任意查询文本，中心（或冒充中心的一方）就能借 reader 对数据源发起任意查询，也能用昂贵的查询压垮数据源。DESIGN §7.5 要求每个数据源固定并发上限（默认 8）、单卡超时 10 秒、配有熔断器。

## 决定

1. **只执行声明过的模板**：reader 挂载一份查询模板清单（由领域包渲染，随 `pack.lock` 通过 GitOps 挂载），每个模板有 ID、内容哈希、方言（`promql` 或 `metricsql`）、表达式和参数声明。中心只发送模板 ID、内容哈希和参数值。清单里没有的模板、哈希不一致的模板一律拒绝（`undeclared_template`、`content_hash_mismatch`）。
2. **内容哈希**：`sha256` 覆盖方言、表达式、按名称排序的参数声明和模板级限制。reader 加载清单时重新计算并核对，被改动过的模板不会加载。
3. **参数按类型渲染**：

   | 类型 | 渲染方式 |
   |---|---|
   | `label_value` | 双引号字符串内部的转义文本 |
   | `label_values` | 每个值先按正则字面量转义，再组成 `(a\|b\|c)`，有个数上限 |
   | `duration` | Prometheus 时长，范围 `(0, max]` |
   | `number` | 有限的十进制数 |
   | `enum` | 声明的取值之一 |

   多出的参数、缺少的参数、类型不符都拒绝（`bad_params`）。渲染结果再用对应方言的官方解析器（`prometheus/promql/parser`、`VictoriaMetrics/metricsql`）检查，模板加载时也用样例值检查一次。参数只能落在模板预留的位置上：试图闭合引号追加选择器的值，在 Prometheus 和 VictoriaMetrics 上都只匹配一个不存在的字面量。
4. **限制**（全局默认值可在配置中覆盖，模板可以声明更严格的 `max_range` 与 `max_series`）：

   | 限制 | 默认值 | 超出时 |
   |---|---|---|
   | 区间跨度 | 7 天 | 起点后移，结果标注 `clamped: [range]` |
   | 步长 | 不小于 1 秒，且单条序列不超过 11000 个点 | 提高步长，标注 `clamped: [step]` |
   | 序列数 | 1000 | 按标签集排序后截断，标注 `truncated` |
   | 响应体 | 16 MiB | 整个查询失败（`response_too_large`） |
   | 单查询时长 | 10 秒，同时作为 `timeout` 参数传给后端 | `timeout` |
   | 每个数据源的并发 | 8 | 在超时内等不到槽位返回 `concurrency_limit` |
   | 熔断 | 60 秒内连接失败、5xx 或超时累计 5 次打开，30 秒后放行一次探测 | `breaker_open` |

   查询本身的错误（参数错误、执行错误、响应过大）不计入熔断，只有说明数据源不健康的错误才计入。截断与调整都写在结果里，阶段 A 据此把卡片标为"无法判定"或在展示中注明，不会把截断的结果当作完整结果。
5. **内置查询**：reader 自己的告警对账与 kube-state-metrics 历史重建使用同一个执行器和同样的限制，查询文本由 reader 代码构造，从不来自中心。

## 结果

- 中心能让 reader 执行的查询，就是领域包里写好的那些；中心被攻破时，攻击者也只能在这些模板与参数类型的范围内查询。
- 每个数据源的负载有上限，数据源变慢或不可用时 reader 快速失败，熔断器状态导出为 `srenautix_reader_query_breaker_state`。
- 领域包更新模板后，需要重新渲染并挂载清单，reader 才接受新模板；心跳上报清单的 `pack_lock` 与模板数，控制台可以显示中心与分支是否一致。
