# 0012 收敛与根因排序

## 背景

DESIGN §5 给出了归并条件（置信度 ≥ τ 的边可达、作用范围、30 分钟相邻）、根因得分的默认权重、覆盖率规则、分差 δ 与沉默根因。参考集群上的 Ops-Agent 用组件依赖表与"最深的原因告警"选根因，遇到一次无关的发布与一次数据库故障同时发生时，最近的变更容易被误认为根因。

## 决定

### 收敛

1. 两条告警时间相邻（两段触发区间的间隔不超过 30 分钟）且满足下列任一条件即合并：
   - 同一组件上的同一实体（没有组件时按告警名）；
   - 一方的实体沿置信度 ≥ τ（0.6）的边可达另一方的实体；另一方的实体就是组件本身时，可达该组件的任一对象也算。
2. forecast 告警最多加入一个分组（路径置信度最高、时间最近的那个），不能把两个分组连起来。
3. 变更在其后 30 分钟内连到组件就是或依赖变更目标的告警。
4. 没有告警的枢纽：只看没有原因告警、也没有变更的分组里的告警。时间相邻的这些告警中，至少 3 个相互独立（组件互不可达）的组件可达枢纽时，枢纽吸收它们，并成为候选。已有原因的症状不需要枢纽来解释，否则每个节点上都有的 CNI Pod 会把并发的独立故障连成一个事件。
5. 收敛结果与告警、变更的到达顺序无关。

### 根因排序

1. 候选：有 cause/change 告警的组件、变更触及的组件、吸收告警的枢纽、沉默根因探测卡异常的组件；都没有时用症状所在组件。只有 forecast 或 meta 告警的组件不成为活动事件的根因。
2. 症状集合是事件中角色为 symptom 的告警。候选能解释一个症状，指症状就在该组件上、症状的实体可达该组件（候选排序使用全部非命名推断的边），或症状在触及该组件的变更之后的窗口内触发。
3. 得分各项：
   - 覆盖率 = 能解释的症状的路径置信度之和 ÷ 症状总数；
   - 先于症状 = 能解释的症状中，触发时间不早于候选起点（原因告警、变更或探测异常的最早时间）的比例；
   - 角色先验取候选自有告警角色、变更（1.0）、探测或枢纽（按 cause）中的最大值；
   - 30 分钟内的变更：有触及该组件的变更或 change 告警时为 1；
   - 长期告警惩罚 = 候选自有告警中长期告警的比例。
4. 排序：先按覆盖率规则分层（解释了全部症状的候选在前），同层按得分，再按深度，命名空间伪组件排在最后。覆盖率规则写成分层而不是加权，因为按默认权重，一次只解释一个症状的发布（变更先验 1.0 加近期变更 1）会高于解释全部症状、但路径置信度较低（经配置引用 0.7）的数据库。
5. 歧义：第一与第二候选同层且分差小于 δ（0.1）。`margin` 记录两者的得分差；跨层时它可以为负，此时不算歧义。
6. 沉默根因：只有症状时，`silentRootTargets` 给出要执行探测卡的上游组件、命名空间内 StatefulSet 的 PVC 容量探测与 ENOSPC 日志卡；阶段 A 执行后把结果传回排序，只有本事件探测目标中的结果生效。

### 持久化对账

每次对账先确定性重算，再按共享的成员告警与已持久化的事件对账。最早创建的事件优先取得重叠最多的分组；分不到分组、但成员落在别的事件分组里的事件合并进去（写入别名，标为 merged）；没有对应事件的分组成为新事件，与某个已有事件重叠时记录 `split_from`。成员或根因变化时 `incident_version` 加一。稳定标签在创建时确定，之后不再改变；同一标签冲突时追加 `~2`、`~3`。

### 证据指纹

判定向量按"卡片@实体"排序后用 jcs-sha256-v1 哈希；新的指纹连续两次对账都出现才生效。

## 结果

- 黄金测试覆盖：CNPG 主库 OOM 同时有 frontend 的无关发布时，数据库排第一（覆盖 3/3，得分 0.562），发布排第二（覆盖 1/3，得分 0.633）且不算歧义。
- 权重、τ、δ、相邻窗口都在 `rca-params` 中，修改需要通过回放门禁。
