# 0042 通知用期望状态表作为发送队列

## 背景

DESIGN §11 要求一个事件只对应一条消息、内容变化时就地编辑、每个渠道一个令牌桶并按优先级发送、同一条消息的多次编辑只保留最新一次、发送队列持久化；PG 不可用时直接发送（§7.1）。聊天渠道还要承担审批与反馈，回调可能重复投递。

## 决定

1. `server.notify_messages` 每个渠道目标 × 事件一行，保存期望内容的全文与哈希、已呈现的哈希、渠道消息 id、优先级通道、下次尝试时间与最近错误。两个哈希不同即待发送或待编辑。
2. 同步循环从事件、阶段 A 报告、研判镜像、提议与反馈重新渲染全部需要消息的事件，只写内容有变化的行；投递循环按通道优先级（urgent → digest → edit → recovery）与令牌桶发送。编辑间隔内的多次变化只留下最新的期望内容，自然合并。
3. 风暴摘要也是同一张表里的一行（kind=digest）。
4. 消息内容由 server 用固定的中英文模板生成渠道无关的 `NotifyMessage`，渠道适配器只负责渲染、投递与回调校验；按钮作用的对象登记在 `server.notify_buttons`，回调只带短 id 或签名后的值。
5. 回调按渠道的回调 id 去重，按钮由第一个回调独占，操作在应答之后执行，结束后释放。审批只限 L 档与已绑定的账号；H 档按钮直接链接到控制台。
6. PG 不可用时由降级通道直接渲染发送（不带回调按钮），渠道消息 id 留在内存，恢复后写回表中，之后照常编辑同一条消息。

## 结果

- 进程重启、渠道不可达、429 都不会丢消息或发出重复的新消息；恢复后补发的是最新内容。
- 渲染与业务状态解耦：新增渠道只需要实现渲染、投递和回调校验。
