# 0151 SQL 审计表作为变更来源：运行时配置变更进入时间线、根因排序与研判的首要假设

## 背景

变更来源只有 Git（GitHub 仓库，ADR 0096）与从拓扑推导的发布（ADR 0104、0140）。业务系统里还有一类改动不经过 Git 与发布：值班经管理接口停用一个导出目的地、发布一份路由或限流配置。它们直接写进业务库并立即生效，SreNautix 看不到。

一个部署里，值班经管理接口停用了全部导出目的地。几小时后，未导出的记录按本地存储预算被淘汰，触发了一条 critical 告警。这是那次维护操作的预期结果，但事件的变更为空，时间线里没有那次停用，研判把一条常态日志当成根因（Zzhihon/SreNautix#17 的 A 项）。业务库里有这类改动的审计记录（配置发布的审计表、管理操作的审计日志），只是没有被读取。

## 决定

### 1. 契约 2.29.0：变更类型 `runtime_config`

`ChangeEvent.kind` 增加 `runtime_config`：经管理接口或数据库直接生效、不经过 Git 与发布的运行时配置变更。只增加枚举值，次版本升到 2.29.0。研判与通知按这个类型识别运行时配置变更，与 Git 上的 `config` 提交区分。

### 2. 变更源 `changes.sql_audit`（`integrations/sql-audit`）

每个来源是一个业务库上的只读连接（写法与 `optimization.dbstats` 相同：host、port、database、user，默认 `srenautix_stats`、password_file、ssl）加一组查询声明：

- `table`（`<schema>.<名称>`：表、视图，或 `function: true` 时返回审计记录的函数，以回看窗口的起止两个 `timestamptz` 为参数调用）、`key`（行的唯一键）、`time`、`object`、`action`，可选 `actor`、`value`（改动之后对象的取值）、`previous_value`（改动之前的取值）、`details`（另外写进摘要的列）；
- `components`：按顺序取第一条匹配的规则（动作或对象取值之一，不写时匹配全部）决定变更的目标；都不匹配的记录不是任何组件的变更。

没有配置时不创建连接、不读取任何业务库，事件、通知与研判的行为不变。

**查询由声明生成**：关系名、函数名与列名只接受小写的普通标识符，并加双引号引用；时间窗与行数上限是绑定参数。读取时间列落在回看窗口（`changes.lookback`，默认 24 小时）内的行，按时间排序，每个查询最多 1000 行。每个查询在单独的只读事务中执行（`statement_timeout` 3 秒、`lock_timeout` 200 毫秒），连接池最多 1 个连接、空闲 60 秒关闭。

**权限**：读取之前（之后每小时）检查角色能读取的业务关系；声明之外还有能读取的关系时不读取，变更源状态记下 `DatasourceOverPrivileged` 与这些关系，同步照常处理其他变更源。

**授权的做法是函数**：属主为超级用户、`SECURITY DEFINER`、`SET search_path = pg_catalog, pg_temp` 的函数，函数体用 `RETURN QUERY EXECUTE … USING` 按时间窗只查出需要的行与列（例如管理审计日志里某一类资源的记录，不含来源地址与客户端）。角色只有这个函数的 `EXECUTE` 与 schema 的 `USAGE`，读不到任何业务关系；审计表开着 FORCE ROW LEVEL SECURITY 也能经函数读取，时间窗在函数里就用上审计表的索引。

选函数而不选视图，是因为视图会登记对它引用的表与列的依赖：业务的迁移删除这些列、改变列的类型、重建表（例如把列存的 hypertable 转回行存）时会失败，一次发布因此停在迁移这一步。函数体是动态查询，不登记依赖：迁移照常执行，之后读取失败只记在变更源状态里，不影响业务。给角色的行级安全策略也不可行：业务的迁移按自己登记的清单收敛策略，会删掉手工建的策略，读取变成静默的空结果。

**与 dbstats 共用角色**：dbstats 的权限自检（不变量 14）原来要求角色不能读取任何业务关系。适配器增加 `allowed_relations`，server 把同一个连接（host、port、database、user 都相同）上 SQL 审计表变更源声明的关系放进去；其他业务表照样让 dbstats 不可用。`READABLE_RELATIONS_SQL` 由 integration-sdk 导出，两边用同一条查询。

### 3. 审计记录转成变更

- `change_id` 为 `<来源 id>:<查询 id>:<键>`，`source` 为来源 id，`kind: runtime_config`，`refs` 为 `<查询 id>/<对象>` 与动作，`actor` 为操作者，时间取时间列。
- 取值规范成文本：时间取 ISO 8601，json、jsonb 按 JCS 规范化；二进制列不能声明。`revision` 为改动之后的取值，`previous_revision` 为改动之前的取值（声明了 `previous_value` 时取它，否则取同一对象上一条记录的取值）；超过 80 个字符时取 sha256 的前 12 位，回退的识别按它比较。
- `summary`：动作与对象、取值的变化（两边都是对象时只列出变化的键，例如 `enabled: true → false`）、`details` 的列，最多 500 个字符，属于不可信文本。

**没有变化与往返**（与发布的标签抖动相同，ADR 0142 §1）：同一对象从一条记录起 `group_within`（默认 2 分钟）之内回到这条记录之前的取值，这几条都不算变更；新旧取值相同的一条记录是它的特例。往返的后半条可能晚一轮才读到，所以这个来源每次同步重算回看窗口内的全部变更：内容变了的更新，不再成立的从窗口内删除。GitHub 来源的写入方式不变（已写入的不再改动）。

### 4. 收敛与根因排序：与其他变更相同

运行时配置变更存进 `server.change_events`，事件引擎与其他变更一起读取：在问题开始之前（或容差之内）、变更窗口（默认 30 分钟）内的变更解释它目标上的告警并进入事件，目标作为 `change` 来源的候选，得到变更先验与近期变更两项；晚于目标上问题开始超过容差的变更不参与排序（ADR 0142 §2）。排序规则没有为这类变更另设参数。

### 5. 阶段 A、通知与研判

- 阶段 A 的时间线照常列出事件里的变更：`<source> runtime_config <查询 id>/<对象> <动作>`。通知里变更的标题写 `运行时配置 <查询 id>/<对象> <动作>`：这类变更的版本常常是整个配置对象的摘要，写对象与动作更能看懂。
- **研判的相关变更**（ADR 0106）：原来是首次触发前 2 小时到现在、触及子图或事件命名空间的变更，最多 20 条。运行时配置变更回看到首次触发前 24 小时，并全部保留（最多 20 条），其余变更取最近的补足。运行时配置的影响常常滞后：停用导出之后，积压的记录要等本地预算用满才被淘汰，可能是几小时以后，远在变更窗口之外。
- **首要假设**：研判输入（事件的变更与相关变更）里有运行时配置变更时，事件数据之后多出一段“运行时配置变更（首要假设）”：列出这些变更（编号、来源、时间、目标、版本、摘要），要求 hypothesize 的第一个假设（h1）以它们为原因提出、根因组件取变更的目标、supporting 引用它们，并为它设计区分性检查去验证或排除；conclude 在 summary 中写明它们被支持还是被排除。这一段不参与裁剪。没有这类变更时不出现，提示词与之前逐字相同。

### 6. chart

`changes.sqlAudit` 的每一项生成 server 配置的 `changes.sql_audit`：`existingSecret` 的口令（键 `passwordKey`，默认 `password`）挂载到 server 的 `/etc/srenautix/secrets/sql-audit-<id>/password`，`password_file` 由 chart 写入；其余键原样写入。`networkPolicy.sqlAuditEgressTo` 限定 server 到业务库的出站，端口取各连接的端口。默认为空列表。

## 不采用的做法

- **由业务系统推送变更**（触发器、逻辑复制、webhook）：要改业务系统或在业务库里建对象并持续运行；只读查询声明的审计关系不需要业务系统配合，授权一次即可。
- **调用业务系统的管理接口读取审计**：每个业务系统的接口不同，需要业务的身份与权限；审计表在数据库里，授权可以收窄到一个函数。
- **为运行时配置变更延长发现阶段的变更窗口**：发现必须可以确定地重放，几小时前的变更解释之后全部告警会把无关的事件连成一个。滞后的影响交给研判：相关变更回看 24 小时，并作为首要假设去验证或排除。
- **单独一个只读角色**：与 dbstats 共用同一个角色时，业务库只需要一个受管角色、一份口令与一条网络放行，角色的连接上限（dbstats 1 个、审计 1 个）也按两个连接池设定；dbstats 的权限自检按声明放行，越权的判定不变。

## 测试

- 单元（`apps/srenautix/test/unit/sql-audit-changes.test.ts`）：生成的 SQL；取值的规范化与报错（时间列不是时间类型、键为空、二进制列）；一次停用的变更形状与摘要；2 分钟内往返、新旧相同、超出 2 分钟、第一条记录；`previous_value` 列；组件规则；长取值的版本；配置校验（标识符、组件键、id 不能重复）；相关变更的选取；首要假设片段（没有运行时配置变更时不出现）。
- 集成（`apps/srenautix/test/integration/sql-audit-changes.test.ts`，真实 PostgreSQL 18.3 与 14.19）：业务库的审计表开着 FORCE ROW LEVEL SECURITY，只读角色只能执行一个返回审计记录的函数。
  - 没有审计变更时，事件的根因是先报 cause 的节点；
  - 同步一次停用（gateway 症状之前 10 分钟）之后，事件里有这次变更，根因候选依次为 gateway（来源 change，近期变更 1）与节点，阶段 A 时间线出现 `app-db runtime_config export-targets/dst-a export_target.update`，研判上下文出现首要假设片段；往返的另一个目标与其他资源的记录不在变更里；
  - 1 分钟后又启用：已写入的停用被删除，根因回到节点；症状开始 13 分钟后的再次停用不参与排序；
  - 角色另外能读取业务表时不读取，状态写明能读取的关系；角色直接读取审计表被拒绝，写入被只读事务拒绝；
  - 删除审计表上函数用到的列：视图会阻止这次迁移，函数不会；之后的读取失败只记在变更源状态里。
- dbstats 一致性（`packages/integration-sdk`，真实 PostgreSQL）：声明的审计视图不计入权限自检；没有声明时计入；另有业务表时仍然不可用。
- chart（helm-unittest）：默认不生成；声明写入配置、口令挂载与网络策略；缺少 Secret 或在 connection 里写口令文件时渲染失败。
- 没有配置时研判行为不变：`~/srenautix-seeds/traces/2026-10-24-refactor-baseline` 的 20 份录制 trace 在本 ADR 的代码上离线重算（`retrace.mts`），请求体与录制时逐字相同，输出逐字段一致。
