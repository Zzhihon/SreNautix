# 0148 事件消息在现状之后列出业务关键信号

## 背景

事件消息（ADR 0125）的证据链按假设与卡片编号排列，和业务服务直接相关的数值（gateway 内存占 limit 94% 并且被 OOM 终止、边缘 5xx 接近阈值、StatefulSet 发布停在未就绪的副本上）散落在折叠的证据链里，聊天里只能看到前几张卡。用户的要求是突出和业务服务紧密相关的信息：存储、内存、CPU、流量负载、是否有阻塞。

## 决定

1. **卡片类别**（契约 2.27.0）：证据卡定义加可选的 `category`，取 `storage`、`memory`、`cpu`、`traffic`、`blocking`；结果（EvidenceResult）带 `category` 与 `value_number`（主值格式化之前的数值）。内置的 workload、node、postgres、kubernetes-core 包给主要卡片写上类别；重启、就绪、版本这类不属于五类的卡不写。cchp 包的卡在 cchp-k8s-ops 另开 PR 补上。
2. **没有类别的卡按名字推断**：先看卡片 id，再看证据链 id，按 `-`、`_` 切词，按内存、CPU、存储、阻塞、流量负载的顺序取第一条命中的词表（例如 `memory`、`oom`；`throttling`、`hpa`；`wal`、`backup`、`disk`、`slots`；`pending`、`pdb`、`rollout`、`waits`、`backlog`；`error`、`5xx`、`latency`、`ttft`）。`requests` 不算流量（资源 requests），推断不出就不列。区分性检查的卡只看 `category`。
3. **只列异常与接近阈值**：异常的卡，以及正常但主值不低于阈值 80% 且低于阈值的卡（标“接近阈值”）。旧报告没有 `value_number` 时从百分比与无单位的展示文本还原。同一对象上同一张卡只列一次，异常优先。
4. **一行一项**：类别、对象、卡片标题、数值与阈值（等宽）、命中的条件说明（已写出数值时省略）、异常起点或窗口。类别按存储、内存、CPU、流量负载、阻塞排列；同类里异常在前，再按数值相对阈值从高到低。每行只有两个等宽实体（数值与阈值），类别是纯文字，五类全满时也只占 20 个实体，给消息其余部分留出 Telegram 的实体上限（ADR 0145 的预算照样约束这一段）。
5. **位置**：段 kind 为 `signals`（契约 2.27.0），粗体标题“业务关键信号”，放在现状之后、时间线与关键问题之前；聊天里每类最多 2 项，其余写一行计数，issue 是全文；没有任何一项时整段不出现。删减优先级高于其他段（最后删减）。Telegram、飞书与 issue 同样的结构。

契约的变化都是可选字段与枚举值的增加，次版本升到 2.27.0。

## 测试

- 黄金用例：按 cchp-k8s-ops#249 那一类 gateway OOM 事件重建的卡片组合（70 个成员告警、53 张卡，内置包的卡带类别、cchp 包的卡靠推断），Telegram HTML 逐字比较并按 Bot API 严格解析；断言内存一类的第一项是 gateway `94.0%` / 阈值 `90.0%` 与“2 个容器被 OOM 终止”，gateway-2 第二，接近阈值的 gateway-1 进入计数；边缘 5xx 接近阈值、StatefulSet 发布阻塞各一行；重启、就绪、连接池这类卡不在这一段。issue 与飞书的段顺序相同。
- 类别推断的词表、接近阈值的边界、去重与排序。
- 已有的黄金用例（发布事故、大事件）多出这一段；实体与长度预算的结果随之变化，删减逻辑不变。
