# 0194 事件消息的结论块：处置、影响、下一步紧跟标题

状态：部分取代（见 0204）。第 1、2 条的三行内容由 ADR 0204 的结论、影响、下一步取代，其余条目仍有效。

## 背景

事件消息的各段依次是现状、业务关键信号、时间线、关键问题、拓扑联系、解决方案、证据链。这个顺序按排查的思路排列，部署方在 2026-10-21 确认过，本 ADR 不改。

值班人在手机上最先要知道三件事：系统建议怎么处置、业务受到什么影响、下一步做什么。这三件事分散在后面的段里。在参考部署的黄金用例中，处置判断在第 27 行，之前有 1165 到 1468 个字。

## 决定

1. `NotifyMessage` 增加 `brief`（契约 2.55.0）：最多三行，依次是处置、影响、下一步。
2. 每一行都取自后面某一段已经写好的块，不另外计算：
   - 处置：关键问题段的处置行（处置判断与阶段 A 的依据）。
   - 影响：业务关键信号段的第一项，前面写"影响 ·"。
   - 下一步：解决方案段的第一项（提议或 runbook），前面写"下一步 ·"；只有"没有提议或建议"时这一行不出现。
3. 没有对应内容的行不出现。还没有阶段 A 报告时没有处置行。
4. 渠道把 `brief` 放在标题之后、各段之前，属于不省略的头部：Telegram 与飞书在超长时先省略低优先级的段，不省略这三行；GitHub issue 放在第一段之前。
5. 各段的顺序不变。聊天渠道里，关键问题段的处置行只在完整报告（GitHub issue）里重复，聊天消息只在结论块写一次。影响与下一步与段内第一项重复，是有意的：段内保留完整的上下文（同一类的其余信号、提议的验证方式）。

## 考虑过的方案

| 方案 | 不采用的原因 |
|---|---|
| 把关键问题段移到现状之前 | 改变部署方确认的段顺序；关键问题段很长，移到前面仍然要翻 |
| 只把处置行移到标题里 | 标题长度有限，放不下影响与下一步 |
| 由模型写一句总结 | 不确定，不可重放；处置与影响已经由确定性的代码求出 |

## 结果

- 参考部署的黄金用例中，处置、影响、下一步出现在第 4 到第 6 行。
- 超过 Telegram 大小上限的消息里，结论块优先于证据链的末尾：黄金用例中证据链末尾的"已执行的检查"被省略，省略处写"其余内容见控制台"。之前的测试要求这一节必须出现，本 ADR 改为要求结论块与省略说明出现。
